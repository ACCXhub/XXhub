# AutoDy 系统设计

适用版本：AutoDy 1.4.2 预发布工作树。本设计描述当前实现的本地组件和安装模型，不把后续扩展视为既成功能。

## 1. 总体架构与技术栈

AutoDy 由 React/Vite 前端、FastAPI 本地服务、Python 领域服务、Playwright 浏览器层、PowerShell 托盘宿主和 WiX MSI 安装器组成。前端只通过本地 HTTP API 获取状态；后端维护配置、任务、历史、模块和诊断；浏览器层受单一锁控制；托盘负责进程发现、端口选择和窗口入口；WiX 将程序文件和可写数据文件分别安装到不同目录。

~~~mermaid
flowchart LR
  UI[React/Vite Dashboard] --> API[FastAPI 本地 API]
  API --> Domain[配置、任务、历史与模块]
  Domain --> Guard[身份、去重、确认与重试]
  Guard --> Browser[受管 Playwright 浏览器资料]
  Tray[PowerShell 托盘宿主] --> API
  Tray --> Discovery[端口与服务身份发现]
  MSI[WiX MSI] --> App[程序目录]
  MSI --> Data[%LocalAppData% AutoDy 数据目录]
  API --> Data
~~~

Python 运行时要求为 3.11 及以上；生产 API 使用 FastAPI，浏览器层使用 Playwright，配置使用 YAML/Pydantic 模型。MSI 构建固定 Python 3.11.9、固定依赖、Chromium 和 WiX 7 输入，以减少构建机差异。前端生产构建由后端静态目录提供，不由托盘直接处理业务逻辑。

## 2. 组件职责

| 组件 | 职责 | 不承担的职责 |
| --- | --- | --- |
| Dashboard | 呈现本地状态、设置、历史和模块信息。 | 不直接操纵浏览器或结束进程。 |
| FastAPI | 提供 service identity、任务、资料、模块、日志和备份 API，托管静态页。 | 不把认证资料返回给页面。 |
| 领域服务 | 解析相对配置路径，维护状态、计划、历史、失败与已解决标记。 | 不绕过身份或去重检查。 |
| 浏览器层 | 使用受管资料目录完成页面访问与稳定身份校验。 | 不在不确定状态下继续发送或重试。 |
| 托盘 | 单实例、服务发现、端口选择、启动/复用/受控停止和菜单状态。 | 不接管无关监听者，也不替代计划任务。 |
| MSI | 安装、升级、修复、快捷方式、固定运行时和目录注册。 | 不删除用户运行时数据。 |

## 3. 启动、端口选择与服务发现

托盘首先建立以项目根派生的本地互斥体。已存在托盘实例时，只请求该实例打开已验证的管理台，而不是启动第二个托盘。启动器读取可选的持久化端口，随后按“持久化端口、8765、8766–8799”的顺序检查候选端口。

每个监听者都通过 HTTP 调用 /api/service-identity 和 /api/modules 进行探测，并结合监听 PID、当前 Windows 用户、返回的应用名/版本、项目路径、模块包路径和 Python 解释器路径判断是否为本安装的 AutoDy。健康且一致的服务被复用；可验证但陈旧的受管理服务才允许托盘停止后重启；任何身份不明的监听者都保持不动。没有可用端口时明确失败。

~~~mermaid
flowchart TD
  A[托盘或启动器请求打开管理台] --> B[取得单实例互斥体]
  B --> C[读取持久化端口]
  C --> D[探测候选端口与 service identity]
  D --> E{是健康且匹配的 AutoDy?}
  E -- 是 --> F[复用 PID 与端口]
  E -- 否，且是已验证旧服务 --> G[受控停止后重启]
  E -- 否或无监听者 --> H[在 8765 至 8799 找空闲端口]
  H --> I[以 selected port 启动 CLI UI]
  I --> J[复核身份并持久化端口]
  F --> K[打开 127.0.0.1:selected-port]
  J --> K
~~~

此模型使重复启动指向同一服务，同时避免“端口为 8765 即可结束”的误判。浏览器窗口关闭不会影响托盘和计划任务；“退出并停止”只适用于该托盘已确认管理的服务。

## 4. 浏览器资料、运行时数据与安全流程

默认配置把消息、状态、锁和工件放在配置目录的相对 data 位置，受管浏览器资料默认在 data/browser-profile。多账号资料将各账号的受管浏览器资料隔离在相应账号目录中。前端仅获得公共资料 payload；诊断导出明确排除浏览器资料、Cookie、头像缓存和消息正文。

发送相关路径依次取得全局锁、核验稳定会话身份、执行重复保护和确认。安全的发送前失败才能保存为延迟重试；可能已发送或身份不明确的结果保持 uncertain。已解决状态只针对同一稳定目标有更晚权威成功且之后无更新失败的历史记录，避免把未解决风险错误地隐藏。

## 5. 安装、升级与卸载模型

WiX 使用 per-user 安装。INSTALLFOLDER 是程序目录，默认在 %LocalAppData%\Programs\AutoDy，新安装时如 D: 可用优先选择 D:\AutoDy；AUTODYDATAROOT 始终是 %LocalAppData%\AutoDy。安装器登记实际程序目录，后续升级和修复先从登记值检索并拒绝陈旧路径。开始菜单包含管理台和卸载快捷方式。

~~~mermaid
flowchart LR
  A[首次安装] --> B{已有有效登记目录?}
  B -- 是 --> C[复用目录，升级或修复]
  B -- 否 --> D{D: 可用?}
  D -- 是 --> E[D:\AutoDy]
  D -- 否 --> F[%LocalAppData%\Programs\AutoDy]
  C --> G[安装固定运行时与程序]
  E --> G
  F --> G
  G --> H[数据目录保持 %LocalAppData%\AutoDy]
  H --> I[卸载移除程序和快捷方式]
  I --> J[默认保留数据目录]
~~~

## 6. 错误恢复、扩展边界与限制

恢复策略以可证明性为界：服务身份不匹配则提示用户检查实际启动源；端口冲突使用安全回退；MSI 失败可使用修复或 verbose log；运行时资料异常不应通过删除整个数据目录来“修复”。便携版可复用生产前端，但仍需 Python 与网络，不能替代 MSI 的固定运行时模型。

可扩展边界在 API、模块注册和受管浏览器层：可选 Test Center 以模块形式存在，不应成为核心安全逻辑的依赖。当前技术限制包括本地单机范围、页面变化引起的浏览器验证失败、未签名 MSI 的系统提示、端口候选范围有限，以及最终 Release CI 仍待通过。
