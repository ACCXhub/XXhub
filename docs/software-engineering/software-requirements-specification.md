# AutoDy 软件需求规格说明

适用版本：AutoDy 1.4.2 预发布工作树。本文描述当前代码、测试或已完成本地验证所支持的行为；最终 Release CI 尚未完成，故不构成发布声明。

## 1. 项目背景与目标

AutoDy 是 Windows 本机运行的 Douyin 私信工作流管理台。它将目标、文案、计划、执行状态和诊断控制在用户本机，并把身份校验、重复保护、确认与浏览器互斥访问作为执行前提。项目的首要目标不是扩大自动化范围，而是在页面、身份或发送结果不确定时能够停止、说明状态并保留用户数据。

本版本还将安装、启动和更新作为产品能力：用户可通过 MSI 获得带固定运行时的安装体验，也可使用需要本机 Python 的 portable 包；重复启动会复用已验证的服务，端口冲突时不会终止无关监听进程。

## 2. 范围、用户与用例

目标用户包括需要在本机查看任务与历史的日常使用者、负责安装和支持的 Windows 用户，以及维护本地发布包的工程人员。支持的使用场景为：查看 Dashboard；维护本地账号配置、目标和文案；创建或查看计划；查看执行历史、失败详情和已解决状态；在托盘中打开或管理本地服务；安装、修复、升级和卸载 MSI；以及使用受控 Test Center 进行非发送验证。

不在当前范围内的内容包括云端多租户管理、远程浏览器接管、自动绕过登录或验证码、未知页面结构下的扩展自动化，以及在真实编辑器中自动准备或发送消息。未来浏览器自动化扩展必须经过单独的安全评审，不能据此文档视为已实现。

## 3. 功能需求

| 编号 | 需求 | 当前实现与验收要点 |
| --- | --- | --- |
| FR-01 | 本地 Dashboard | 显示本地任务概览、健康状态、历史和需要处理的事项；不依赖云端服务。 |
| FR-02 | 账号与目标管理 | 支持本地账号资料和隔离的受管浏览器资料目录；对外 API 不暴露私有标识或浏览器资料。 |
| FR-03 | 文案与计划 | 支持本地文案、文案包、计划设置和运行记录；数据路径由配置相对位置解析。 |
| FR-04 | 执行历史 | 记录计划或安全重试触发的状态，并区分已解决的历史失败与仍可安全重试的失败。 |
| FR-05 | 安全重试 | 仅能证明未发生发送动作的失败进入 retry_pending；成功重试可标为 recovered；不确定结果不重试。 |
| FR-06 | 浏览器安全 | 使用全局锁、稳定会话身份、重复保护和确认路径；身份歧义、草稿、附件或可能发送时停止。 |
| FR-07 | Test Center | 可选 Settings 子页，只支持用户明确启动且受门禁保护的受控干跑；不调用发送管道。 |
| FR-08 | 托盘启动 | 托盘单实例运行，可打开管理台、查看状态、重启服务、切换启动项和退出。计划任务不依赖托盘。 |
| FR-09 | 服务复用 | 重复启动时仅复用经 /api/service-identity、用户、项目/包路径和 Python 解释器验证的 AutoDy 服务。 |
| FR-10 | 动态端口 | 优先使用 8765；被无关监听者占用时，从 8766–8799 选择空闲端口；所选端口可持久化并在下次启动复核。 |
| FR-11 | MSI 生命周期 | 支持首次安装、修复、主版本升级和卸载；新安装优先 D:\AutoDy，不可用时回退至 %LocalAppData%\Programs\AutoDy。 |
| FR-12 | 数据保留 | 程序目录与 %LocalAppData%\AutoDy 可写数据分离；卸载清除程序文件和快捷方式，默认保留用户数据。 |

## 4. 非功能需求

**可靠性。** 浏览器流程必须串行访问，并用明确的任务结果状态表达 scheduled、running、retry_pending、recovered、completed、final_failed、uncertain 与 cancelled。安全重试采用受完成窗口约束的延迟策略；失败通知只能在最终失败后产生一次，恢复成功须压制旧的临时失败提示。

**可用性。** Dashboard 通过 127.0.0.1:<selected-port> 提供本机访问。托盘应在浏览器窗口关闭后继续运行。已验证服务可被重复启动路径复用；端口被占用时应报告或安全回退，而不是粗暴结束所有 Python、PowerShell、Chrome 或 Edge 进程。

**可维护性。** 配置、运行时数据、浏览器资料和构建输出彼此分离。MSI 采用固定 Python 3.11.9、固定依赖与 Chromium，并通过明确 allowlist 组装发行物。构建产物使用 SHA-256、发布 manifest 和确定性构建检查，便于排查来源与差异。

## 5. 运行环境与安装升级要求

MSI 面向 Windows x64 的当前用户安装，依赖 Windows Installer；安装包内包含固定运行时和 Chromium，普通安装不要求 Node.js。portable 包包含生产前端，但需要 Python 3.11 和网络以安装依赖；源码开发还需要 Node.js、PowerShell 5.1 或更高版本，以及在构建 MSI 时使用的 .NET/WiX 工具链。

MSI 必须先检索已登记的安装目录，拒绝失效或陈旧路径；存在有效旧版本时进行升级或修复而非产生平行安装。新安装应优先选用可写的 D:\AutoDy，否则落入 %LocalAppData%\Programs\AutoDy，且用户可在安装向导中选择其他可写目录。升级与修复复用既有程序目录，不迁移或删除可写数据目录。

## 6. 隐私、安全与异常处理

所有执行均在本机边界内。账号认证和浏览器资料位于受管资料目录，不能进入 Git、发布包、诊断导出或文档截图。日志与诊断应使用脱敏摘要；备份、日志和导出不得包含浏览器资料、Cookie、头像缓存或真实消息内容。

异常处理遵循“不能证明安全就停止”：无关进程占用端口时保持其存活；服务身份无法验证时不附着也不停止；安装目录无效时拒绝继续；可能发送或身份歧义时不重试。用户应得到可操作的错误信息，而不是要求清空数据或结束全部相关进程。

## 7. 验收标准与已知限制

验收至少包括 Dashboard 本机可达、配置路径可解析、服务身份接口可用、端口冲突安全回退、同 PID 服务复用、MSI 安装/修复/升级/卸载和数据保留、SHA-256 校验、发行物隐私扫描以及受控浏览器安全分支。详细证据见[测试与验收报告](test-and-acceptance-report.md)。

当前限制：服务仅运行于本机；浏览器交互仍受页面结构、登录状态和平台变化影响；未签名 MSI 可能出现 Windows 信任提示；portable 不是免运行时的完整替代；最终 v1.4.2 Release CI 尚未完成。1.4.2 准备状态不能替代正式发布或跨机器兼容性承诺。
