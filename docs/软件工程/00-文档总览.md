# AutoDy 软件工程文档总览

## 1. 文档定位

本目录是 AutoDy 当前软件工程交付文档的 canonical owner。结构参考软件文档编制、需求与测试文档的常见规范类别，并按本项目规模合并重复内容；目标是让需求、设计、接口、数据、测试、部署、运维和项目总结形成一条可追溯链，而不是为了数量制造平行说明。

代码和可执行配置仍是实现事实的最终来源；文档用于说明这些事实、边界和验收方法。若文档与当前 `main` 不一致，应先以源码、测试和已发布资产核实，再在本目录原位更新文档。

## 4. 与仓库其他文档的关系

- 根 `README.md`：公开项目入口，只保留用户真正需要的安装、能力、状态和文档导航。
- `CHANGELOG.md`：版本差异历史；“是否发布”以 GitHub Release 与标签/资产事实为准。
- `docs/RELEASE_NOTES.md`：当前候选版本的 Release body；只有正式 workflow 发布成功后才代表公开 Release 说明。
- `docs/codex/PROJECT_HANDOFF.md`：维护代理的当前工程交接，不替代软件工程交付文档。
- `docs/archive/`：完成阶段的历史计划、设计与旧 Release 说明，只用于追溯。
- `docs/文档总览.md` 与 `docs/AUTODY_ENGINEERING_MANUAL.md`：兼容入口，正文以本文件及 01–13 为准。

## 6. 文档维护规则

1. 新功能先改变 canonical 实现，再同步受影响的需求、设计、接口/数据和测试追踪；不创建 `final/fixed/new` 文档副本。
2. 当前事实写在当前文档，过程性设计完成后进入 `docs/archive/`；不把修复历史堆进正文。
3. 数据结构必须来自实际 Pydantic/dataclass/文件格式/Windows Installer 与 Task Scheduler 语义，不虚构数据库表。
4. API 文档描述产品本地接口；精确可执行 authority 是 `web_api.py` 的 route decorators 与请求模型。
5. 测试报告只能记录已有证据；候选失败必须保留为失败，不能把“构建成功”写成“完整验收通过”。
6. 文档、夹具、诊断不得包含真实账号、目标、消息、Cookie、令牌、浏览器 profile 或未经审查的原始日志。
