# AutoDy 运维维护与故障排查

## 1. 排障总原则

AutoDy 的排障顺序是：**先确认身份与边界，再恢复 owner，最后才考虑清理**。端口、PID、显示名、一个文件夹存在都不能单独证明归属。

禁止把以下动作当通用修复：按名称批量结束 `python.exe`/PowerShell/Chromium、删除整个 `%LocalAppData%`/DataRoot、复制 Cookie/profile、手工改 Windows Installer 注册、反复运行 uncertain 任务。

## 2. 维护前最小记录

只记录非敏感事实：

- AutoDy 版本/分发方式；
- 操作阶段；
- selected port；
- service identity 是否匹配；
- ProgramRoot/DataRoot 类型（不必公开真实用户路径）；
- Scheduler 是否存在/drift/read error；
- 错误码/受控摘要；
- 是否可复现。

不记录真实好友、消息、Cookie、browser profile 内容和未经审查的完整日志。

## 3. Dashboard 不打开

1. 从托盘选择“打开 AutoDy 管理台”。
2. 若需要诊断，查询候选端口 listener 和 `/api/service-identity`。
3. HTTP 响应存在后仍要核对当前用户、ProgramRoot/package path、Python executable 等归属事实。
4. 8765 被无关程序占用时，8766–8799 回退是正常行为。

只有确认是当前 AutoDy managed service 后，托盘才可以重启/停止它。unknown listener 保持存活。

## 4. 多次启动、旧端口与旧服务

持久化 service-port 只是启动提示，不是信任票据。每次启动重新探测/验证。若持久端口现在属于其他程序，AutoDy 重新扫描候选端口；不会“因为上次是自己的”就停止当前监听者。

重复启动应复用同一 verified AutoDy 服务。若出现页面指向旧安装，应先核对 service identity/ProgramRoot，不通过结束所有 Python 进程“清场”。

## 5. Watchdog 反复恢复

检查顺序：

- 进程是否真的退出，还是仍在但 health 失败；
- health 失败是否已经连续约 15–20 秒；
- 该 PID 当前仍否满足 service identity/path/owner/creation-time 约束；
- 最近 10 分钟是否已自动恢复 3 次；
- 用户是否执行过 explicit full exit。

熔断后应保留 needs-attention 现场，而不是增加自动重启次数。若强停发生，必须能证明 graceful stop 已失败且 exact PID 在停止前重新验证通过。

## 6. 登录/账号问题

登录过期：只在 AutoDy 受管 Chromium 中重新登录。

账号切换失败：先确认是否存在发送 marker、dry-run 或其他 browser action；这些操作进行中时 409 是正确安全阻断。

退出后好友绑定全部显示待验证：这是 revalidation guard 的预期语义。重新登录/完整 discovery 后由 canonical binding proof 恢复，不通过按名字批量重建。

多账号迁移失败：保留 `account-profile-migration-backups`/rollback manifest，由 account owner 恢复；不要手工混合两个 profile 目录。

## 7. 好友找不到、绑定异常、重名

区分四类事实：Target stable ID、durable binding proof、discovery candidate、conversation locator。

- `binding_missing`：缺 durable proof，需要显式重新关联；
- `stale_locator`：proof 仍存在但当前 candidate/locator 过期，需要当前 discovery；
- `identity_ambiguous`：多个候选不能唯一证明；
- `account_mismatch`：当前登录账号不是目标所属账号；
- `scan_incomplete/failed/stale`：先恢复 discovery 质量，不修改 binding。

重名不是“选第一个”的理由。完整扫描后使用 Friends relink，后端仍会检查唯一性/占用/account scope。

## 8. 发送失败与 `uncertain`

先看结构化 `FailureDetail`：reason/stage/send_attempts/uncertain/safe_retry。

- `send_attempts=0` 且 `safe_retry_available=true`：可按已有安全补发入口处理；
- 发生发送尝试但确认失败：`uncertain`，停止自动重试；
- binding/account 问题：先去 Friends/账号处理，不直接补发；
- recovery deadline 已过：final_failed，不通过修改系统时间或重复启动覆盖。

历史失败必须保留。恢复 binding 不等于把旧 uncertain 变成可重试。

## 9. Preflight 失败

Preflight 只读检查登录、聊天列表、唯一会话、composer 和发送控件。常见 reason：friend_not_found、blocked_ambiguous_target、conversation_load_timeout、composer_missing/hidden/disabled、send_control_missing、login_required、page_structure_changed、browser_busy。

它不发送消息。若 preflight 本身出现任何 fill/type/press/send 证据，应视为实现回归而不是“更真实的测试”。

## 10. Scheduler 问题

### 10.1 Snapshot read error

Task Scheduler 查询超时、PowerShell error、invalid JSON 是“读取失败”，不是“0 个任务”。先恢复查询/权限；不要立即重建全部任务。

### 10.2 Drift

成功 snapshot 中名称、trigger、script、ProgramRoot、DataRoot、WorkingDirectory、Principal、RunLevel、重复窗口与期望不一致才是 drift。Repair 可以恢复已知任务；真实 drift 不能通过忽略 verifier 获得“通过”。

### 10.3 UAC

Dashboard 常态非提升。安装/修复/移除/应用 Task 时才请求操作级 UAC。取消 UAC 应保持现有任务/配置不变。若一直需要管理员运行 Dashboard 才能工作，说明权限边界回归，应修 owner 而不是改变操作手册。

## 11. MSI 安装/Repair/卸载

建议保留 verbose log：

```powershell
msiexec.exe /i '.\AutoDy-<version>-x64.msi' /L*v '<日志路径>'
```

分享前审查私有路径/资料。

检查顺序：包来源/hash → 目标 ProgramRoot → 原用户 DataRoot → Installer 注册 → Scheduler custom actions → 具体 msiexec exit code。

Repair 的目标是恢复程序/快捷方式/Scheduler 契约；它不负责清空数据。

普通卸载预期：产品注册、ProgramRoot、快捷方式和三项 AutoDy tasks 消失；DataRoot 保留。若 tasks 指向已删除 ProgramRoot，说明 lifecycle 不完整，保留安装日志并修复 installer owner，不手工删除所有 Task Scheduler 记录掩盖问题。

## 12. v1.5.2 Release / installed acceptance checkpoint

`v1.5.2` 已通过正式 workflow 的 clean-source build、受保护发布和 public asset reverify。hosted MSI lifecycle 是非阻塞诊断；没有生成报告时不得把它描述为已执行的安装态 acceptance。

本机 public MSI 升级必须在管理员上下文运行。未提升上下文中旧产品移除会报 Error 1730/1603 并回滚；这不是可通过重试、手工复制 ProgramRoot 或停止非本产品进程解决的问题。

升级前后都应记录 DataRoot 可验证基线。若 8765 的 `/api/service-identity` 指向源码 ProgramRoot，则它不是 `D:\AutoDy` 的可控实例；先保留它，再在已验证 installed owner 上完成 endpoint/Dashboard 验收。

## 13. Lifecycle 诊断分类

| 失败阶段 | 优先检查 |
| --- | --- |
| `ui_wizard/cancel_path` | MSI tables、WiX UI/ControlEvent、short|long MSI filename 解析 |
| `fresh_install` | ProductState、ProgramRoot payload、Scheduler repair、原用户 roots |
| `shortcuts` | WScript shortcut target/arguments/working dir |
| `repair` | feature install state、payload/local component、Scheduler repair |
| `custom_install` | INSTALLFOLDER、registered path、payload 是否误写默认目录 |
| `upgrade` | v1.4.4 baseline、scope migration、DataRoot/Task continuity |
| `uninstall` | remove-task CustomAction 顺序、RemoveFiles、残留程序文件 |
| `data_preservation` | snapshot 比较、DataRoot 是否被 installer 修改/删除 |

Verifier 解析 MSI 表时要遵守 Windows Installer 实际编码（例如 `short|long` 文件名），不能把合法格式误判为缺文件。

## 14. 日志与磁盘清理

优先使用产品 log retention/cleanup preview。`output/work` 是可再生成构建/诊断 staging，不是版本历史：成功后脚本应删除一次性 work；失败时只保留当前诊断目录供定位，问题关闭后再清理。

不要保留每个版本/每次 CI 的多套 staging 作为“保险”。正式历史由 Git commit/tag/Release 和必要报告保存。

## 15. 备份/导入失败

先 preview。invalid checksum/manifest/类别应拒绝。导入前产品会建立恢复备份；config/messages 写入异常应回滚原文件。不要解压 ZIP 后手工覆盖 DataRoot，这会绕过 schema/路径/账号规则。

## 16. 发布资产问题

如果 Release 页面没有目标版本 canonical assets，则该版本不是可供普通用户下载的正式包。CI artifact/runner output 只是候选。

公开 Release 完成后再验证：资产文件集合 → `.sha256` → manifest → MSI/privacy。只有这些来自同一 tag/SHA 才可关闭发布。

## 17. 症状—owner 快速表

| 症状 | owner |
| --- | --- |
| 端口/服务复用/重启 | tray/watchdog/service identity |
| 登录/多账号 | account_profile(s) |
| 好友扫描 | friend_discovery |
| 重新关联/绑定健康 | binding_recovery |
| 发送/确认/uncertain | runner + chat + failures/retry |
| 今日统计不一致 | web_api projection + daily/history owner |
| Windows Tasks | scheduler + scripts |
| 安装/Repair/卸载 | WiX + MSI scripts/lifecycle verifier |
| 文案/文案包 | messages / MessagePackService |
| 日志 | log_center |
| 备份 | transfer |
| Release | release workflow + build/verify scripts |

维护结束时复查：当前服务身份正确、DataRoot 保留、unknown listener 未被终止、业务状态没有被“重试覆盖”。
