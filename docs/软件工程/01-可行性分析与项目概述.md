# AutoDy 可行性分析与项目概述

## 1. 项目背景

AutoDy 是面向 Windows 本机的 Douyin 私信工作流管理台。它解决的不是“能否自动点击发送”这一单点问题，而是日常低频续火场景中的一组工程问题：目标身份会变化、页面结构会变化、登录会失效、同一动作可能重复执行、浏览器和计划任务会并发、安装升级需要保留用户数据，本机端口和进程还可能与其他程序冲突。

因此项目目标是把一次脆弱的浏览器脚本收敛为可管理、可诊断、可恢复且失败时安全停止的本机软件。用户通过 Dashboard 管理目标、文案、计划、历史、日志和备份；后台通过 Windows Task Scheduler、受管 Chromium 和明确的状态机执行受控任务。

## 2. 目标用户与使用场景

主要用户是希望在自己的 Windows 电脑上维护固定 Douyin 私信工作流的个人用户，以及负责本机安装、排障和发布的维护者。系统不面向云端多租户、远程控制、绕过登录/验证码或未知页面上的通用自动化。

典型场景包括：

- 登录后扫描聊天列表，将可证明身份的候选加入续火目标；
- 使用本地文案库或内置/自定义文案包生成当日内容；
- 配置每日健康检查、每日续火和每周健康检查；
- 对已证明发生在发送动作之前的失败进行有限安全重试；
- 对结果不确定、身份不一致、页面异常等状态 fail closed；
- 查看当前失败、历史、日志和受控诊断；
- 通过 MSI 完成安装、Repair、升级和卸载，同时保留 DataRoot；
- 使用 standalone Portable 在独立目录中运行。

## 3. 方案比较

### 3.1 纯手工操作

优点是实现成本最低、平台兼容性最好；缺点是每天重复操作、没有统一状态/历史，也无法自动保证重复保护。AutoDy 的价值主要来自计划、状态和安全边界，而不是比人工“更会点按钮”。

### 3.2 简单浏览器脚本/宏

实现快，但通常把显示名、DOM 位置、一次点击结果当作事实，缺少稳定身份、全局锁、确认、安装数据边界和可诊断恢复。当页面变化或运行中断时，最危险的是无法判断“是否已经发送”。AutoDy 选择显式状态机、绑定证明和 fail-closed，增加工程复杂度以降低误发与重复发送风险。

### 3.3 云端/RPA 平台

云端平台便于集中管理，但需要处理账号、浏览器状态和消息数据离开本机的额外隐私边界。AutoDy 的需求集中在单机个人工作流，因此采用本地 Dashboard + 本地浏览器 + Windows Scheduler 更符合最小数据流原则。

## 4. 技术可行性

项目当前技术栈已形成可运行实现：Python 3.11、FastAPI、Pydantic/PyYAML、Playwright、React/Vite、PowerShell 5.1、WiX 7。MSI/Portable 携带固定 Python、依赖、Chromium、生产前端与资源，降低对用户系统环境的依赖。

关键技术可行性已经由现有代码和测试证明：

- FastAPI 可作为仅监听 loopback 的本地 UI/API 服务；
- Playwright persistent context 可承载受管登录和聊天页面自动化；
- Windows Task Scheduler 可在托盘关闭时继续按原交互用户、Limited 权限运行；
- PowerShell/WiX 可维护 ProgramRoot、DataRoot、快捷方式和任务生命周期；
- `binding_recovery` 可以把 durable friend identity、当前 discovery candidate 与 conversation locator 分离；
- 独立 release pipeline 能生成 standalone MSI/Portable，并执行隐私、结构和可重复性检查。

主要技术不确定性不是框架本身，而是 Douyin 页面模型与浏览器行为随平台变化。项目通过 selector/identity 检查、只读 preflight、失败状态和回归测试降低影响，但无法消除平台变化风险。

## 5. 操作可行性

普通用户的主路径集中在 Dashboard：好友、文案、文案包、定时任务、总览、日志、备份和设置。托盘提供单实例入口并隐藏动态端口细节；Scheduler 写操作仅在需要时触发一次 UAC，Dashboard 本身保持非提升。

安全操作原则与用户心智一致：未知服务不接管、未知结果不重试、卸载默认保留数据、登录只在受管浏览器完成。维护人员能够通过 service identity、安装日志、状态/历史和脱敏诊断定位问题，而不要求用户导出 Cookie 或整个 DataRoot。

## 6. 经济与资源可行性

项目采用开源运行时与工具链，不依赖商业数据库或云端服务。主要资源消耗是本机 Chromium、standalone Python 运行时和约数百 MB 级发布包；发布阶段的可重复构建和 MSI 生命周期测试对 CI 时间要求较高，因此当前已把重型检查从普通 push/PR CI 中分离到正式 Release workflow。

维护成本主要来自平台页面变化、Windows 安装兼容和发布可靠性，而不是服务器运维。对于单机个人软件，这一成本结构可接受。

## 7. 安全、隐私与合规可行性

AutoDy 只应在用户自己的已登录会话中工作，不设计验证码绕过、认证窃取或平台限制规避。账号、目标、消息、浏览器 profile、Cookie、日志和备份保持在本机运行边界；发布包使用 allowlist 和隐私扫描排除运行数据。

风险仍包括本机账户被他人访问、磁盘未加密、第三方安全软件、平台规则变化和未签名 MSI 的信任提示。软件只能控制自己的数据流和安全停止策略，不能替代操作系统、账号与平台合规责任。

## 8. 主要风险与缓解措施

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| Douyin DOM/React 数据变化 | 找不到好友、无法确认发送 | selector/identity 分层、preflight、失败码、停止而非猜测 |
| 显示名重名或 locator 变化 | 发错对象 | durable identity + account scope；candidate/locator 不作为永久身份证明 |
| 发送后确认不确定 | 重复发送 | `uncertain` 终态，禁止自动重试 |
| 浏览器并发 | 会话互相干扰 | 全局 browser lock 与 action manager |
| 服务端口冲突 | 启动失败或误伤进程 | service identity + 8765–8799 回退，不按端口/PID猜归属 |
| 后台服务异常 | Dashboard/计划不可用 | watchdog 仅对已验证 AutoDy 服务进行有界恢复 |
| 安装/升级删除用户数据 | 高损失 | ProgramRoot/DataRoot 分离，卸载默认保留数据，lifecycle acceptance |
| 发布包夹带运行数据 | 隐私泄露 | allowlist、privacy verifier、manifest/hash、公开资产再校验 |
| 重型 Release 验证耗时 | 开发迭代变慢 | 普通 CI 与 Release validation 分层 |

## 9. 可行性结论

AutoDy 的核心功能、运行模型和主要安全边界已经有实际实现，技术和操作路线可行。项目适合继续作为 Windows 本机维护型软件，而不需要引入云端、多租户或通用浏览器自动化架构。

v1.5.0 与 v1.5.1 MSI lifecycle acceptance 的失败候选均保留为历史。当前 v1.5.2 formal workflow 以 source/build、MSI/Portable、privacy/package、manifest 和公开资产核验为发布硬门禁；候选构建不能冒充稳定资产。
