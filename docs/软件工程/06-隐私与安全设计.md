# AutoDy 隐私与安全设计

## 1. 信任边界与本地服务模型

AutoDy 的信任边界是当前 Windows 用户设备。Dashboard、FastAPI、计划、托盘和受管浏览器都在本机运行，服务只通过 127.0.0.1:<selected-port> 提供本机访问。应用不应把真实账号、目标、消息、Cookie、令牌、浏览器 profile、备份或原始日志作为文档、Git、发布包或普通诊断输出的一部分。

本地运行并不自动消除风险：设备被他人使用、磁盘未加密、恶意软件、错误共享和过度日志都可能泄露资料。用户负责保护 Windows 帐户、屏幕锁定和下载来源；维护人员负责限制应用数据流、发布输入和诊断范围。

## 2. 受保护数据与处理规则

| 数据类型 | 存储位置 | 允许用途 | 禁止目的地 | 删除/保留行为 |
| --- | --- | --- | --- | --- |
| 程序 payload | D:\AutoDy 或 %LocalAppData%\Programs\AutoDy | 运行、Repair、升级 | Git、运行时备份 | 卸载时移除。 |
| 配置、计划、历史 | %LocalAppData%\AutoDy 或配置相对 data | 本地 Dashboard 与调度 | 发布包、公开日志 | 卸载默认保留。 |
| 受管浏览器资料 | data/browser-profile 或账号隔离目录 | 用户控制下登录与本机自动化 | Git、诊断导出、截图 | 不因普通卸载删除。 |
| 认证/Cookie | 受管浏览器受保护存储 | 受控浏览器会话 | API 响应、工单、备份 | 不导出、不打印。 |
| 消息正文与目标 | 本地运行时资料 | 用户本机工作流 | 文档、测试夹具、CI 输出 | 不进入发布物。 |
| 脱敏诊断 | 受控日志/CI 结果 | 定位构建或路径问题 | 无限制公开渠道 | 按日志策略保留。 |

多账号场景中浏览器资料按账号目录隔离。公共资料 API 使用受控 payload，不应返回私有标识。受控干跑也不放宽边界：只有用户明确发起且锁、稳定会话、空编辑器和无附件条件均成立时才可进行临时内存检查；不按 Enter、不点击发送、不调用发送管道，任何不确定状态都停止。

## 3. 服务身份与端口所有权

端口号与 PID 都不能证明服务归属。托盘查询 service identity 和模块信息，并核对当前 Windows 用户、版本、项目/包路径和 Python 解释器。只有所有关键信息一致的服务才可复用；只有托盘确认管理的服务才可在重启或退出并停止时结束。该机制保护无关的本地 Python、Web 服务或开发环境。

首选端口为 8765；冲突时在 8766–8799 中找空闲端口并可持久化选择。已验证结果显示无关监听者保持存活，重复启动复用同一 AutoDy 服务。候选端口耗尽时应失败并报告，不能抢占、扫描或终止其他程序。

## 4. Git、发行物与隐私扫描

Git 忽略运行时数据、.venv、node_modules、日志、缓存、模块注册表和私有截图。portable/MSI 构建使用 allowlist，而非递归复制仓库；这样减少 data、测试夹具和临时输出进入候选包的机会。Release 验证检查 manifest、路径、内容和 SHA-256；官方模块包也由受控输入和清单/哈希核对。

CI 在发布检查失败时保留受控隐私诊断，用于说明哪个规则或文件路径不符合要求。这些诊断不是收集用户资料的授权，仍必须最小披露。维护人员不得为排障上传完整 data、浏览器 profile、认证文件或原始日志。

## 5. 完整性、可重复性与安装器限制

用户应通过 Get-FileHash 比较 MSI/portable 的 SHA-256 sidecar。MSI 构建固定关键运行时与输入，并已有字节级可重复性验证；D3DCompiler_47.dll payload 也已验证。确定性输出提高审计与差异定位能力，但不替代来源验证、访问控制或代码审查。

MSI 当前未声称代码签名。Windows SmartScreen、企业策略或终端防护可能提示风险；正确处理是使用正式 Release、校验哈希并遵循组织策略。项目不使用 packer、UPX、规避安全软件或隐藏载荷技巧，因为它们会降低可审计性、增加误报并损害供应链可信度。

## 6. 当前风险、责任与后续加固

当前稳定版本为 v1.5.0。限制包括本机设备安全依赖、浏览器页面变化、登录有效期、未签名 MSI 和有限端口范围。用户负责操作系统和下载安全；开发者负责不扩大数据流、保持隐私扫描和服务身份检查；发布负责人负责只发布通过门禁并与记录来源一致的产物。

维护阶段可评估签名与证书治理、更细粒度日志保留和更多企业环境兼容验证。AutoDy 2.0 或 BrowserWeave 的功能研究不在本仓库继续；任何新的自动化边界仍需在独立范围内更新威胁模型、测试和保留规则。

## 7. 日志脱敏、审计与最小披露

日志的目的仅是帮助定位阶段、错误类别、端口选择和构建规则，不是复制业务会话。可接受的诊断字段包括版本、模块兼容状态、匿名化的运行标识、操作阶段和受控错误码；不应记录消息正文、原始账号标识、Cookie、完整 profile 文件名或浏览器页面内容。导出前还需确认结果没有因异常堆栈、命令行或临时目录意外引入私有路径。

发布审计遵循两条线：完整性线验证文件是否来自当前受控输入、hash 是否一致、manifest 是否匹配；隐私线验证文件是否属于 allowlist、文本中是否包含禁止路径/资料模式、运行时目录是否被排除。二者缺一不可。仅有正确 hash 不能证明包中没有私密文件；仅有扫描通过也不能证明文件来自正确提交。

发生隐私疑虑时，首选动作是停止发布、隔离候选输出并保留最小诊断摘要。不要把候选包上传到更多位置做“比对”，不要用禁用扫描或放宽规则解决问题；只有在明确授权且对应生产输入需要改变时才重新生成产物。任何未通过当前门禁的候选包都应按未发布内部资料处理。

## 8. 安全事件的处置原则

若发现候选包、日志或文档可能含私有资料，应立即停止分发并标识影响范围；先确认是否已离开受控环境，再决定是否撤销候选和重建。处置记录只包含文件类别、规则命中、时间和已采取动作，避免在事件记录中再次复制敏感内容。若发现未知服务监听候选端口，处置是拒绝附着并保留进程，不是试图读取其数据或强制结束。

安全设计也要求防止方便性降级：为了让启动更快而跳过身份核验、为了让安装成功而接受陈旧路径、为了让重试更积极而忽略 uncertain，都会扩大风险面。评审时应把这些变更当作安全变更，要求对应测试、文档和发布检查，而不是普通文案调整。

安全复核的最小问题集是：这项变更是否增加新的数据流？是否让未知进程获得控制权？是否可能让候选包包含运行时资料？是否改变用户数据删除语义？若任一答案为是，必须补充明确的拒绝路径、脱敏规则和回归验证，不能只以正常路径演示作为依据。

## 9. 最小权限与用户告知

应用只应使用完成当前本机功能所需的文件和网络能力。MSI 使用 per-machine 提升安装，但提升前显式捕获原交互用户 SID 与 LocalAppData；计划任务使用 Limited Principal，数据仍写入该原用户目录。托盘只查询本机监听和受控 API；浏览器资料只供受管会话使用。用户应清楚知道程序目录与数据目录不同、卸载默认保留数据、端口可能回退、MSI 尚未声明签名。清晰告知本身是安全控制：它降低用户为解决误解而执行危险清理、关闭防护或共享敏感资料的概率。

Scheduler 写操作使用一次性 `runas` PowerShell 子进程，而不是常驻管理员服务。正常 Dashboard 在提升前从自身进程令牌捕获原用户 SID，并把该 SID、ProgramRoot 和 DataRoot 放入只允许 install/remove 的受约束请求；提升子进程只分派到既有 `install-task.ps1`/`remove-task.ps1`，不持有第二套任务定义，也不从提升环境重新推断身份或路径。结果通过 DataRoot 下带 nonce 的短生命周期 JSON 返回并立即删除；其中不包含账号、目标、消息、Cookie 或浏览器资料。提升只改变注册/移除权限，计划任务 Principal 继续为原用户且 `RunLevel Limited`。

发生支持请求时，先让用户提供非敏感的版本和错误阶段；如果必须提供日志，要求其先审查并使用受控渠道。项目不以“调试需要”为理由要求 Cookie、账号密码、浏览器 profile 或真实消息。任何新增的诊断字段都应接受同样的最小披露审查。
