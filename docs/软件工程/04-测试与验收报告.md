# AutoDy 测试与验收报告

## 1. 目的、范围与准入条件

本报告用于判断 AutoDy 1.4.2 候选版本是否具备进入最终 Release CI 的证据基础。测试范围包括 Python 领域/API、前端、托盘服务复用、端口回退、MSI 打包、安装生命周期、发行物完整性和隐私排除。测试不使用真实账号、真实目标、真实消息或真实浏览器资料；涉及浏览器的自动化采用夹具、模拟或只读路径。

准入条件是：版本、构建输入、manifest 和候选产物一致；干净源码环境能完成基础准备；MSI 生命周期在干净 Windows 用户配置中执行；测试机没有以真实业务数据充当夹具。退出条件是每个必需项目有可追溯的条件、操作、期望、观察和证据；任何阻断缺陷必须关闭或明确阻止发布。

## 2. 策略、环境与分类

策略分为四层。第一层是 Python/API 单元与集成测试，验证配置、状态机、服务身份、模块、历史和隐私排除。第二层是 React/Vite 前端测试，验证可见状态与组件行为。第三层是 PowerShell/WiX/打包测试，验证目录模型、固定 payload 和确定性。第四层是 Windows 生命周期验证，验证安装、Repair、升级、卸载、快捷方式与数据保留。发布前还执行 manifest、SHA-256、allowlist 和私密路径扫描。

环境使用项目 .venv、固定依赖、Windows x64、WiX 7、固定 Chromium 和干净的生命周期用户配置。测试结果只说明该环境与输入下的行为，不能推导所有 Windows 策略、代理、终端防护或平台页面均通过。

## 4. 失败处理与未覆盖区域

测试失败时先保留命令输出、构建 manifest 和受控诊断，再按失败层级定位：Python/API 失败回到领域逻辑；前端失败检查 API 契约；MSI 失败检查安装目录/组件/日志；隐私失败检查 allowlist 和候选目录。不要为了让测试通过而清空 data、停止无关服务、使用真实资料或跳过 SHA-256。

未覆盖区域包括所有 Windows 版本和企业策略组合、未签名 MSI 的组织级信任体验、网络代理、第三方安全软件交互、真实登录有效期和未来浏览器扩展。它们是当前限制，不是“测试通过”的隐含范围。

## 5. 发布门禁

v1.4.2 仍是发布候选。最终 Release CI 必须在本次文档提交之后对正确提交、正确 manifest 和正确候选包运行；仅当其成功时才能创建标签与 Release。此前的本地、MSI 或聚焦测试是进入门禁的证据，不是替代门禁。

## 6. 验收记录使用方式

验收表中的“已观察结果”必须来自一次已保存的命令输出、生命周期报告、CI 记录或专门测试，不应根据文档或代码阅读推断。若后续测试得到新计数，应更新相应行的观察结果和证据来源，而不要保留两套相互矛盾的数字。对于版本候选，测试通过与发布完成是两个状态：前者证明某个输入集已验证，后者还需要最终 CI、正确提交和正式资产一致。

故障分级按发布影响处理。涉及私密资料进入候选包、无关进程被停止、安装/卸载删除数据、或 uncertain 被自动重试的缺陷属于阻断；服务回退端口未显示、快捷方式缺失或文案不一致通常也应在发布前修复，但需要结合是否影响安装路径判断。任何失败都先保留可审计证据，禁止通过关闭扫描、放宽 allowlist 或替换为真实用户数据来获得“通过”。

回归选择应与改动范围一致。仅文档修改时验证链接、围栏、敏感路径和差异即可，不需要重装或重跑生命周期；修改托盘、WiX、打包或隐私规则时则必须恢复相应聚焦测试和发布检查。这个区分避免无关操作污染安装环境，也避免把文档任务错误宣称为完整产品回归。

## 7. 测试类别的覆盖边界

Python/API 测试主要验证输入归一化、路径处理、状态转换、公开响应和拒绝条件；它不能替代 Windows Installer 的真实注册表、快捷方式或文件保留行为。前端测试主要验证渲染和交互契约；它不能替代本机托盘、端口占用或浏览器登录。MSI 包装测试可以检查清单、固定 DLL、目录与确定性，但仍需生命周期脚本验证实际安装、Repair、升级和卸载。将这些证据组合，才能避免某一类通过被误解为完整交付通过。

对于每次发布候选，应生成证据包索引：提交哈希、版本、构建时间、manifest hash、MSI/portable SHA-256、测试摘要和 Release CI 链接。索引本身不应包含安装机用户名、运行时目录、真实资料或原始日志。若 CI 与本地证据指向不同提交，必须重新构建或重新验证，不能把不同候选的结果拼接为一次验收。

测试复盘应记录缺陷属于输入、实现、环境还是证据关联问题。输入问题通常通过固定版本和 allowlist 解决；实现问题通过新增回归测试解决；环境问题需在干净用户配置中复现；证据关联问题需重新绑定 commit 与产物。该分类使发布讨论聚焦于可验证事实。

## 8. 结果复核责任

开发者负责保证代码和对应测试在同一提交中；构建负责人负责保证候选输出与 manifest/hash 对应；测试负责人负责复核环境、操作和观察结果；发布负责人负责在最终 CI 后核对标签、资产和结果。任何角色发现证据缺口都可以阻断发布。这个分工避免将安装器、端口或隐私问题留给最后一位执行者临时判断。

对失败用例的修复验证必须包含原失败条件。例如端口冲突修复不能只在空闲 8765 上运行；服务复用修复不能只确认页面可打开；数据保留修复不能只确认卸载退出码。只有在原始风险环境下观察到预期保护行为，才可将验收项从待补充证据改为通过。
