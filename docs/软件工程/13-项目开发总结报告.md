# AutoDy 项目开发总结报告

## 1. 项目结果概述

AutoDy 已从单点浏览器自动化演进为 Windows 本机工作流管理软件：具有 Dashboard、目标/好友绑定、文案与文案包、计划任务、状态/历史、只读发送前检查、日志/备份、多账号本地隔离、托盘/watchdog、standalone MSI/Portable 和正式 Release validation。

项目最重要的结果不是“实现自动发送”本身，而是建立围绕它的可靠性与安全边界：稳定身份、重复保护、发送确认、`uncertain` 终态、全局 browser lock、服务 ownership、原用户 Scheduler/DataRoot、安装生命周期和发布隐私门禁。

当前代码版本线与正式发布目标为 1.5.1。v1.5.0 tag 的正式 Release 在 MSI lifecycle acceptance 阶段失败且没有发布资产，因此保留为历史；v1.5.1 仍必须以自身 formal workflow 结果决定是否完成稳定发布。

## 2. 已实现功能

### 2.1 本地管理台

React/Vite Dashboard 通过 loopback FastAPI 展示运行总览、好友、文案、文案包、Scheduler、日志、备份、设置与可选模块。异步 browser action 通过 job 状态统一反馈，不让前端直接调用真实 sender。

### 2.2 好友发现与稳定绑定

好友 discovery 能处理虚拟列表/lazy-load、candidate/currentness、头像缓存和权威 identity。系统最终把：

- AutoDy Target `stable_id`；
- durable friend proof；
- discovery candidate/current conversation locator

分成三层，解决了此前把弱 candidate/name 当稳定好友身份造成的安全和可恢复性问题。

`resolve_stable_binding` 成为读取权威入口，`reassociate_stable_binding` 成为显式写入入口；账号不一致、扫描不完整、identity 歧义或只有名字/头像时 fail closed。

### 2.3 发送与失败状态机

Runner/Chat 保留同日去重、全局 browser lock、stable binding、页面/编辑器检查和发送确认。失败按“是否能证明发送尚未发生”分类：safe pre-send failure 可进入有限 retry；发送尝试后无法确认进入 `uncertain`，禁止自动重试。

历史 FailureDetail 保留原失败证据；后续成功只改变“是否已解决”的展示，不删除历史。

### 2.4 Preflight

只读发送前自检与 sender 解耦。它只允许导航到会话和读取 DOM，不暴露 fill/type/press/send 通用 API，并把写动作计数作为验证证据。

### 2.5 Scheduler 与权限

Windows Task Scheduler 成为自动运行权威。每日健康检查、每日续火、每周健康检查使用原交互用户 Principal、`RunLevel Limited`。Dashboard 保持非提升，只有 Scheduler 写操作使用受约束一次性 UAC 子进程。

任务快照成功空结果与读取失败已经分离；瞬时 read error 可有限重试，真实 drift 不能被忽略。

### 2.6 托盘与 watchdog

托盘提供单实例、动态端口和 service identity 验证；8765 冲突时安全回退 8766–8799，不停止未知进程。

watchdog 对 verified AutoDy service 有界恢复：process exit 与 health hung 分开、约 15–20 秒连续 health failure、graceful first、exact PID 再验证、3 次/10 分钟熔断、manual full exit suppression，并严格限制恢复动作只作用于服务生命周期。

### 2.7 多账号、日志与备份

多账号本地 registry/profile/snapshot 使账号级 Target、计划、browser profile 和 runtime 数据隔离，legacy 单账号迁移有 rollback backup。

日志中心提供筛选、保留、归档和脱敏诊断；备份 v2 使用类别、manifest/checksum 和 preview/import，browser profile 不进入普通备份。

### 2.8 Windows 产品化

MSI/Portable 均为 standalone：包含固定 Python、依赖、Chromium、生产前端和资源。MSI ProgramRoot 与原用户 DataRoot 分离；普通卸载删除程序/快捷方式/Tasks而保留 DataRoot。

Release pipeline 提供可重复构建、privacy/package verifier、lifecycle acceptance、guarded manifest、公开资产发布和 re-download 再验证。

## 3. 主要技术难点与解决方式

### 3.1 “好友名字”不是身份

早期实现容易把昵称/candidate/DOM locator 混在一起。页面模型变化后会出现“UI 看起来绑定正常、Runner 无法安全定位”或更危险的误绑定风险。

最终方案是把 durable proof 与 current locator 分层，并要求 account scope + authoritative identity + unique match。显示名只用于展示/诊断。

### 3.2 “失败”不等于“可以重试”

浏览器自动化最危险的状态是发送动作可能已经发生但确认失败。项目用 `send_attempts`、confirmation、FailureDetail 和 outcome state 把 safe retry 与 uncertain 分开；不确定时宁可停止。

### 3.3 本机服务归属

“8765 上有服务”或“PID 是 python.exe”都不足以证明属于 AutoDy。托盘/watchdog 组合 HTTP service identity、用户、路径、解释器和进程快照，只有 verified owner 才能复用/停止。

### 3.4 提升后的用户身份与 DataRoot

per-machine MSI/UAC 下，管理员进程的 `%LOCALAPPDATA%` 不是原交互用户数据目录。项目在提升前捕获 SID/LocalAppData，并显式跨边界传给 Scheduler/installer，避免计划任务 Principal 和 DataRoot 分裂。

### 3.5 Installer/Release 的真实验收

“MSI 能构建”不代表安装/Repair/升级/卸载正确。项目建立了表结构/CustomAction verifier、standalone payload/privacy 检查和真实 lifecycle。当前 v1.5.0 也因此在 lifecycle 未全绿时被阻止发布，这说明门禁确实在执行，而不是装饰性 CI。

## 4. 工程结构成果

当前主要 owner 已清晰：

- `config.py`：配置/Target schema；
- `friend_discovery.py`：当前 discovery；
- `binding_recovery.py`：stable binding；
- `account_profile(s).py`：账号元数据/隔离；
- `runner.py`/`chat.py`：发送状态机；
- `preflight.py`：只读 readiness；
- `state.py`/`history.py`/`retry_state.py`/`failures.py`：运行事实；
- `scheduler.py` + scripts：Windows Tasks；
- `web_api.py`：本地 HTTP adapter；
- `frontend/`：Dashboard；
- `scripts/` + `packaging/wix`：托盘/watchdog/安装/构建/验证；
- `.github/workflows/release.yml`：正式发布。

普通 CI 与 Release CI 已分层，避免每次开发 push 都执行重型 MSI/Portable reproducibility/lifecycle。

## 5. 测试与质量结果

已形成从 unit/domain/API/frontend 到 PowerShell/WiX/release/lifecycle 的多层测试。CI 收敛后的普通 Python selection 为 529 项；2 个重型 `release_build` tests 只在 Release 执行。

v1.5.0 正式 tag Release run 已通过 heavy reproducibility、Portable/MSI build 和 privacy/package verification，但 lifecycle acceptance 失败并阻止资产发布。详细证据与限制见 09。

因此当前质量结论是：**核心产品功能和多数发布构建边界已有较强回归证据；v1.5.1 仍需完成一次正式 Windows 安装生命周期、发布与公开资产再校验。**

## 6. 文档交付成果

本次收口建立完整软件工程文档链：

`可行性 → 开发计划 → 需求 → 概要设计 → 详细设计 → 接口 → 数据字典 → 测试计划 → 测试报告 → 安装/用户 → 运维 → 安全 → 总结`。

其中数据字典明确覆盖 YAML/JSON/JSONL/files/Registry/Task Scheduler，而不是为无数据库项目虚构 SQL 表；接口设计以实际 FastAPI routes 为基础；测试报告明确区分稳定 Release 和候选证据。

## 7. 与初始简单自动化的主要差异

项目在演进中增加了大量“非核心点击功能”，但这些并非功能膨胀，而是把脚本产品化需要的控制面：

- 身份与账号范围；
- 状态/历史/失败恢复；
- 日志/备份；
- 托盘/服务 lifecycle；
- Scheduler/UAC；
- MSI/Portable；
- 隐私/供应链验证。

与此同时项目也明确停止把云端、多租户、通用浏览器自动化继续塞入 AutoDy；后续通用研究属于独立项目边界。

## 8. 当前未完成事项

### P0：v1.5.1 formal lifecycle

需要取得/复现 `msi-lifecycle-report.json/md`，读取具体 failed stage/assertion，判断是 verifier 对 MSI/WiX 事实的错误假设还是 installer 真缺陷，并只修 canonical owner。

### P0：正式 v1.5.1 Release

在最终 v1.5.1 release source/tag 上执行一次 formal Release，发布 canonical MSI/Portable/checksum/manifest，并完成 public asset reverify。完成前不能把源码版本或 runner 候选描述为稳定资产。

### P1：签名与环境兼容

MSI 尚未声明代码签名；未来可评估代码签名/证书运维、更多 Windows/安全软件/代理环境兼容性，但不作为当前 blocker 的替代工作。

## 9. 后续维护建议

- 可靠性/安全 bug 继续从 canonical owner 修复，不在 UI/脚本外围建立第二套状态。
- 平台页面变化优先更新 discovery/chat/preflight 的可验证证据与测试。
- 数据 schema 变化同步 07；API 变化同步 06；高风险行为同步 03/05/08/12。
- 远端 GitHub Actions 启动后不需要由交互代理持续轮询；等待完成后一次读取结果即可。
- 构建/诊断 staging 成功后收敛，失败时仅保留当前问题需要的证据；版本历史由 Git/Release 保存。

## 10. 总结

AutoDy 已具备完整本机软件工程形态，其主要创新和工程价值集中在“对浏览器自动化不确定性建立可证明的安全边界”，而不是单纯提高点击自动化程度。

当前项目不需要重新设计产品架构；最重要的收尾是在 v1.5.1 上完成 formal lifecycle、Release 与 public asset verify。此后应以维护、兼容和高风险可靠性修复为主，保持现有模块与文档体系收敛。
