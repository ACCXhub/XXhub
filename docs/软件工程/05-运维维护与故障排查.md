# AutoDy 运维维护与故障排查

## 1. 安全排障原则

排障先确认监听端口、服务身份、安装目录和用户数据边界，再选择恢复操作。严禁使用按名称批量结束 python.exe、powershell.exe、chrome.exe 或 msedge.exe 的命令；严禁把删除 %LocalAppData%\AutoDy、浏览器 profile 或整个仓库当作首选修复。无关进程、计划、历史和认证资料都可能因此受损。

## 2. Dashboard 不打开或显示已在运行

症状是浏览器未出现、本机地址打不开或提示已有实例。常见原因包括托盘尚未完成服务发现、服务在持久化回退端口、8765 被无关监听者占用、或服务身份不匹配。安全检查：

~~~powershell
Get-NetTCPConnection -LocalPort 8765 -State Listen -ErrorAction SilentlyContinue |
  Select-Object LocalAddress,LocalPort,OwningProcess
Invoke-RestMethod -Uri 'http://127.0.0.1:8765/api/service-identity' -TimeoutSec 2
~~~

若第二条成功，结果必须符合当前 AutoDy 安装与用户；否则不能据 PID 结束进程。正确修复是从托盘选择“打开 AutoDy 管理台”，让托盘使用已验证端口。预期未出现时，检查 8766–8799 的持久化选择并查看托盘日志；不要手动占用或强制释放端口。

## 3. 8765 占用、8766 持续使用与多次启动

8765 占用时，AutoDy 选择 8766–8799 的空闲端口是预期行为。服务端口可被持久化，下一次启动仍可能使用 8766，只要身份验证继续通过。多次启动应复用同一服务 PID；若出现多个页面或连接失败，使用托盘“重启管理台”，它仅能停止已确认管理的服务。所有候选端口不可用时记录错误并联系维护人员，不通过结束全部本地开发进程解决。

## 4. 服务身份失败、登录过期与计划未运行

身份失败意味着应用名、当前用户、版本、项目/包路径或解释器中至少一项不匹配。此时不要附着、不停止监听者；记录端口和错误摘要，确认启动的是当前安装快捷方式。受管浏览器登录过期时只在 AutoDy 受管窗口重新登录，不复制 Cookie 或 profile。计划未运行时先查看 Dashboard 历史、计划设置和失败状态，再检查仅属于 AutoDy 的 Task Scheduler 项；关闭浏览器或退出托盘不等于计划被禁用。

安装、修复、移除或应用计划时出现 UAC 是预期的操作级授权，Dashboard 本身仍应以普通用户运行。若页面报告 `HRESULT 0x80070005` 或 Access Denied，先确认当前版本是否具有 Scheduler 提升边界，不要永久以管理员启动托盘。授权后若报告 Principal 漂移，应把 Task Scheduler 返回的账户名解析为 SID 再与原交互用户 SID 比较；不得因显示格式不同改用提升账户，也不得从提升进程的 `%LOCALAPPDATA%` 推断 DataRoot。UAC 被取消时保持任务和配置不变，重新操作前先确认页面请求已经结束。

## 5. MSI、DLL、目录和 Repair

MSI 安装失败时检查 Windows 提升是否成功、目标目录、磁盘空间和安装日志。Repair 后若任务提示 Principal 或 DataRoot 漂移，应确认安装器捕获的是原交互用户 SID 与 LocalAppData，不要从提升管理员的环境变量手工重建任务。陈旧安装路径说明登记目录可能已不存在；不要新建一个同名目录欺骗安装器。D3DCompiler_47.dll 写入/载入失败时先校验 MSI SHA-256、检查隔离记录和磁盘空间；不得下载来源不明 DLL 覆盖程序目录。Repair 的预期结果是恢复程序 payload/快捷方式且不清空 %LocalAppData%\AutoDy。

v1.4.4 已区分 Scheduler 成功空快照与读取失败。若日志报告快照超时、PowerShell 查询失败或无效 JSON，应按明确读取错误处理；不要把它解释为任务均不存在。注册后验证会有限重试，但成功快照中的真实缺失或漂移仍会阻止安装。

记录 verbose MSI 日志的安全命令：

~~~powershell
msiexec.exe /i '.\AutoDy-1.4.4-x64.msi' /L*v '<日志路径>'
~~~

日志共享前应检查其中没有账号、认证、消息或私有路径。

## 6. 卸载、数据保留、快捷方式和清理

Windows 设置与开始菜单“卸载 AutoDy”均可触发卸载。三个 AutoDy Windows 任务、程序目录和快捷方式被删除，而 `%LocalAppData%\AutoDy` 中的计划设置、历史和其他用户数据保留，是预期结果。若任务仍指向已删除 ProgramRoot，说明卸载生命周期未完整执行，应保留 MSI 日志并修复安装后重新卸载；不要手工删除 Windows Installer 注册信息。重新安装会根据保留配置重新创建任务。

只有用户明确永久放弃数据、应用已退出且备份完成后，才检查单一候选目录，例如 %LocalAppData%\AutoDy 或明确不再使用的 D:\AutoDy。绝不能递归删除 %LocalAppData%、浏览器通用 profile、用户主目录、仓库根、output 或不确定路径。

## 7. 校验与升级

下载包先执行：

~~~powershell
Get-FileHash -Algorithm SHA256 '.\AutoDy-1.4.4-x64.msi'
~~~

结果必须与同名 sidecar 一致。1.4.0–1.4.2 是 per-user，1.4.3/1.4.4 是 per-machine：迁移时必须先从 Windows 设置卸载旧程序，再安装 v1.4.4；`%LocalAppData%\AutoDy` 保留。若新 MSI 报告发现旧 per-user 安装，不要绕过检查或手工删注册表；完成正常旧版卸载后重试。

## 8. 症状到处置的快速矩阵

| 症状 | 可能原因 | 安全诊断 | 修复方向 | 禁止动作 |
| --- | --- | --- | --- | --- |
| 管理台连接被拒绝 | 服务未启动或端口变化。 | 用托盘入口、再查指定端口监听。 | 让托盘重新发现/启动。 | 结束全部 Python。 |
| 端口响应但身份不符 | 旧安装或无关服务。 | 读取 service identity。 | 使用当前安装快捷方式。 | 停止该未知 PID。 |
| 一直使用 8766 | 持久端口仍经验证可用。 | 通过托盘确认地址。 | 保持使用或在安全重启后复核。 | 强制绑定 8765。 |
| 登录被要求重新验证 | 受管会话已过期。 | 查看本机登录状态。 | 在受管窗口重新登录。 | 复制认证文件。 |
| 计划没有记录 | 计划被禁用、时间未到或服务不可用。 | 查看历史和 Task Scheduler。 | 修复计划设置或服务。 | 清空 data 重置。 |
| Scheduler 管理返回拒绝访问 | 普通 Dashboard 缺少单次提升或 UAC 被取消。 | 查看 API 错误码和 UAC 结果。 | 使用当前版本的操作级提升路径。 | 永久以管理员运行 Dashboard。 |
| MSI 无法维护 | 安装路径陈旧或策略阻止。 | 记录安装日志与目录状态。 | Repair 或按组织策略处理。 | 手工删 Installer 注册。 |
| Portable 启动失败 | ZIP 未完整解压、目录不可写或 payload 不完整。 | 核对 `AutoDy.cmd`、`runtime\python`、`runtime\ms-playwright` 与分发标记。 | 重新完整解压可信 ZIP。 | 安装系统 Python/Node 或从仓库补文件。 |

## 9. 维护记录与升级前检查

每次有风险的维护操作前，记录版本、当前 selected port、是否为当前用户服务、操作类型和结果摘要即可。记录不应包含目标、消息、认证或 profile 路径。升级前应确认没有正在运行的受管理任务，保留需要的本地备份，并确认候选 MSI 与 SHA-256 一致。升级后先从托盘打开 Dashboard，确认服务可达和历史仍在，再决定是否清理明确废弃的程序目录。

若需要外部支持，最小材料是：应用版本、Windows 版本、操作阶段、错误摘要、选中端口、是否可复现、经审查的 MSI verbose 日志位置。不得发送完整 data、浏览器资料、Cookie、用户消息或截图中的私人内容。支持人员收到材料后应先判断是服务身份、端口、安装器还是登录状态的问题，而不是要求用户“重装一遍”。

## 10. 分阶段排障流程

第一阶段只读确认：记录症状、版本、操作时间、托盘状态和选中端口；检查服务身份，不改变进程。第二阶段最小恢复：通过托盘打开或重启已验证服务、通过 Repair 恢复程序文件、在受管窗口重新登录。第三阶段维护恢复：在有 hash 校验和 verbose log 的前提下执行 MSI 升级或卸载。第四阶段才是明确数据清理，且必须是用户主动、路径明确、服务退出后的独立决定。

如果一个症状同时涉及安装与服务，例如升级后页面打不开，不要先判断为浏览器问题。先确认程序目录是否是升级后的有效目录，再确认托盘是否验证了同一安装，最后才检查端口和登录。反向顺序会把旧安装、未知监听者或持久端口误判为页面缓存，导致错误的重启或删除操作。

对于排程问题，维护人员应区分计划未触发、触发后被锁拒绝、触发后安全失败等待重试、结果不确定。前三者可通过本地历史、计划设置和锁状态分类；最后一种不能通过再次执行来覆盖。任何建议都应说明预期结果和停止条件，以便用户知道何时应等待、何时应反馈，而不是不断尝试。

维护结束时应复查三件事：托盘能否打开当前服务、数据目录是否仍保留、未知监听者是否从未被终止。只有三项都符合预期，才记录本次操作为成功恢复。若其中任何一项不确定，保留现场和摘要，升级给具备安装/服务证据的维护人员。

## 11. 例行维护边界

例行维护可以检查版本、包 hash、磁盘空间、托盘状态、计划状态和受控日志摘要。例行维护不包括读取浏览器 profile、导出认证、扫描用户消息或删除历史。需要清理时先使用产品提供的保留策略和明确路径，确认操作只影响可再生成的日志/缓存；不确定某目录性质时默认不删。

恢复快捷方式时，优先选择 MSI Repair，因为它同时遵循已登记安装目录和组件规则。手工新建快捷方式容易指向陈旧程序目录或固定错误端口。恢复后仍应从托盘打开并验证服务身份，不能把快捷方式存在当成应用健康证明。

对于反复出现的同类故障，应记录版本、安装方式、端口选择、错误阶段和是否可在干净环境复现，再由维护者决定是否创建测试。不要把同一错误通过多次重新安装掩盖；这样既会丢失证据，也可能误伤保留的数据。
