# AutoDy 软件需求规格说明书

## 1. 项目背景、问题定义与目标

AutoDy 是 Windows 本机运行的 Douyin 私信工作流管理台。实际使用中，目标、文案、计划、浏览器状态、登录状态和页面结构都可能变化；单纯以“任务是否结束”判断成功，会掩盖发错会话、重复发送、端口误占用或安装后数据丢失等风险。项目因此把本地可管理性和可证明的安全停止作为目标：用户应能在本机查看状态、维护计划和诊断问题；系统仅在身份、重复保护和确认条件成立时进入受控流程；不能证明安全时必须停下并保留现场。

产品目标包括：提供本机 Dashboard 和执行历史；隔离受管浏览器资料；支持计划与安全重试；通过托盘提供稳定启动入口；在端口冲突时保护无关进程；让 MSI 的安装、修复、升级和卸载不破坏用户数据。非目标包括云端集中控制、自动绕过登录或验证码、跨机器服务发现、未知页面结构下的浏览器扩展，以及在真实编辑器中自动准备或发送消息。

## 2. 范围、对象与使用假设

目标用户是普通 Windows 使用者、需要排障的支持人员和维护发布包的开发者。用户具有当前 Windows 帐号的安装权限，并通过正式 Release 获取包；应用仅监听本机回环地址。普通用户使用 MSI，技术用户可选择 portable；源码仅用于开发。用户应通过 AutoDy 受管浏览器完成登录，不导入日常浏览器的私密资料。

| 范围内 | 范围外 |
| --- | --- |
| 本地目标、文案、计划、状态、历史、模块和诊断管理 | 云端同步、多租户权限和远程控制台 |
| 本机托盘、服务身份、动态端口和受控服务复用 | 按端口号或进程名终止无关程序 |
| MSI 安装、修复、升级、卸载与数据保留 | 未实现的浏览器平台适配或批量绕过登录 |
| 安全停止、延迟重试、已解决状态 | 对可能已发送结果的自动重试 |

## 3. 功能需求

| 编号 | 描述、触发与预期行为 | 失败行为 | 验证方法 |
| --- | --- | --- | --- |
| FR-001 | 用户打开 Dashboard 后，系统显示本地健康、计划、历史和需处理事项。 | 本地 API 不可用时显示可诊断状态，不伪造数据。 | API/前端测试与只读页面检查。 |
| FR-002 | 用户维护账号、目标、文案或文案包时，资料保存于本地配置和数据边界内。 | 私有标识、浏览器资料和认证信息不经公共 API 返回。 | 配置/API 测试。 |
| FR-003 | 计划到期后创建具运行标识的执行记录，并在历史中展示状态。 | 计划冲突或锁不可用时记录明确失败/等待结果。 | 调度与历史测试。 |
| FR-004 | 发送前失败且可证明未发生发送动作时，进入 retry_pending 并按窗口约束延迟重试。 | 可能发送、确认失败或身份歧义时进入 uncertain，不重试。 | 重试状态与失败详情测试。 |
| FR-005 | 同一稳定目标存在更晚权威成功且之后无新失败时，历史失败可标为已解决。 | 未满足证据链时仍保留重试/风险状态。 | Overview 已解决状态测试。 |
| FR-006 | 托盘启动时取得单实例互斥体，并提供打开、状态、日志、重启和退出入口。 | 已有实例时复用入口，不启动第二托盘。 | 托盘控制器测试。 |
| FR-007 | 启动器通过服务身份、当前用户、路径、模块和解释器识别可复用服务。 | 身份不匹配时不附着、不停止、不接管。 | 服务身份与无关监听者测试。 |
| FR-008 | 首选 8765；占用且非本服务时，从 8766–8799 选择空闲端口，可持久化后复核。 | 所有候选均不可用时返回明确错误。 | 端口冲突测试。 |
| FR-009 | MSI 新安装优先 D:\AutoDy，D: 不可用时回退 %LocalAppData%\Programs\AutoDy，并可选自定义可写路径。 | 陈旧登记路径被拒绝，不向未知位置写入。 | WiX/生命周期验证。 |
| FR-010 | Repair 恢复程序 payload；v1.4.1 升级复用有效目录；卸载移除程序和快捷方式。 | 任一维护阶段失败时保留数据并写入安装日志。 | 生命周期验证。 |
| FR-011 | 用户数据位于 %LocalAppData%\AutoDy，默认卸载后仍保留。 | 不允许因普通卸载删除浏览器资料、历史、计划和备份。 | 数据快照验证。 |
| FR-012 | Test Center 作为可选设置页，受用户显式启动和浏览器安全门禁约束。 | 未安装时不加载模块页面；不确定状态立即停止。 | 模块/API 测试。 |

## 4. 非功能、可靠性与安全需求

NFR-001 可用性：管理台仅通过 127.0.0.1:<selected-port> 服务；托盘在浏览器窗口关闭后仍可运行，计划任务不依赖托盘。NFR-002 可维护性：配置路径可相对解析，构建使用固定输入、manifest 和 SHA-256，程序与可写数据目录分离。NFR-003 可诊断性：服务身份、选中端口、安装日志和发布检查提供最小必要的可操作信息。

REL-001 要求浏览器访问由全局锁串行化。REL-002 要求任务状态明确区分 scheduled、running、retry_pending、recovered、completed、final_failed、uncertain 与 cancelled。REL-003 要求最终失败通知以任务运行标识和终态去重，恢复后压制旧失败。SEC-001 要求稳定会话身份、重复保护和确认先于任何可能的发送动作；SEC-002 要求无关监听者保持存活；SEC-003 要求日志、诊断、备份和发布包排除认证资料、浏览器 profile 与消息正文。

## 5. 安装、数据保留、异常与验收

INS-001 要求 MSI 为当前用户安装，程序目录与 %LocalAppData%\AutoDy 数据目录分离。INS-002 要求升级、修复使用有效登记目录；INS-003 要求卸载快捷方式存在且卸载后默认保留用户数据。异常发生时，端口冲突选择安全回退；服务身份失败提示实际来源检查；登录失效要求用户在受管浏览器重新登录；草稿、附件、身份不一致或不确定结果均停止且保留现场。

验收需覆盖 Dashboard、本地服务身份、端口回退、同 PID 复用、MSI 安装/修复/升级/卸载、数据保留、D3DCompiler_47.dll、SHA-256、发布隐私扫描及安全重试。当前限制是本机单机范围、浏览器页面可能变化、未签名 MSI 可能提示信任风险、端口候选范围有限，且 v1.4.2 最终 Release CI 尚未通过。后续规划仅包括签名、兼容矩阵和经过安全评审的新扩展，不属于本版本承诺。

## 6. 需求追踪与补充验收规则

每项需求应在代码、测试、发布记录三者中至少留下一个可追溯入口。FR-007、FR-008 与 FR-009 的共同前提是“不以猜测处理外部状态”：服务存在不等于服务可信，端口空闲不等于可以忽略持久化选择，已登记目录不等于目录仍有效。维护人员修改其中任何一项时，必须复核三项而非只修改单个启动脚本或安装页面。

对于用户可见操作，验收必须包含成功和失败两个观察面。例如启动后页面可打开是成功面；8765 被无关监听者占用且其进程仍在、AutoDy 转至 8766 是失败环境下的成功面。Repair 的成功面是 payload 和快捷方式恢复；失败环境下的约束是不能删除数据目录。升级的成功面是程序替换；失败环境下的约束是不能产生未知平行目录或丢弃旧数据。

数据保留需求还要求区分“卸载程序”和“永久删除数据”。前者是常规 Windows 维护动作，默认只影响程序文件与快捷方式；后者必须由用户明确决定，并在服务退出、备份完成和路径已确认后单独执行。文档、支持流程和自动化测试不得把这两种操作混称为“清理”。

最终验收的判定顺序为：先检查隐私与数据边界，再检查身份、端口和安装路径，最后检查页面和功能表现。这样即使界面可显示，也不会忽略错误启动源、误附着服务或将私密运行时数据带入候选包的高风险问题。

需求变更应记录影响范围。若改动端口策略，至少复核 FR-006、FR-007、FR-008、NFR-001 与 SEC-002；若改动安装器，至少复核 FR-009、FR-010、FR-011、INS-001 至 INS-003；若改动浏览器或重试路径，至少复核 FR-004、FR-005、REL-001 至 REL-003 与 SEC-001。这样可以把功能增加转化为可执行的验收集合，而不是依赖个人记忆。

当需求之间发生冲突时，优先级依次是保护用户数据与避免误发送、保持无关进程不受影响、提供可诊断恢复、最后才是减少用户点击。该优先级解释了为什么某些失败状态不自动重试、某些端口不被强行占用、某些卸载操作默认保留数据。

需求验收记录应写明触发条件和失败行为，避免只保留成功截图。对 AutoDy 而言，拒绝未知服务、保留数据和停止 uncertain 都是满足需求的结果。
