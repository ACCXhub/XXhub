# AutoDy 系统设计说明书

## 1. 设计目标与技术组成

系统设计以“本地、可验证、可恢复且不误伤”为目标。AutoDy 不把端口占用、显示名称或一次页面读取当作唯一事实，而是将前端、本机 API、领域服务、受管浏览器、托盘和安装器拆分为职责明确的层。前端负责呈现；FastAPI 提供本地 API 与静态资源；领域服务保存配置、计划、状态、历史和模块；浏览器层执行受锁保护的身份校验；托盘负责单实例、端口、服务发现和窗口入口；WiX 负责安装、升级和卸载中的文件/数据边界。

技术栈为 Python 3.11、FastAPI、Pydantic/YAML、Playwright、React/Vite、PowerShell 5.1 与 WiX 7。MSI 使用固定 Python 3.11.9、固定依赖和 Chromium，发布工具生成 SHA-256、manifest 和受控 allowlist。技术选择的作用不是堆叠框架，而是让服务生命周期、配置解析和发行物来源可检查。

~~~mermaid
flowchart LR
  U[本机用户] --> UI[React/Vite Dashboard]
  UI --> API[FastAPI 本地 API]
  API --> D[配置、计划、历史、模块]
  D --> G[身份、去重、确认、重试]
  G --> B[受管 Playwright 浏览器]
  T[PowerShell 托盘] --> S[端口/服务发现]
  S --> API
  W[WiX MSI] --> P[程序目录]
  W --> R[%LocalAppData% AutoDy 数据目录]
  API --> R
~~~

图中 UI 不直接控制浏览器；任何浏览器操作都需经领域服务和安全门禁。托盘不保存业务数据，也不替代计划任务；它只负责发现可验证服务或启动新的本机服务。MSI 只管理程序 payload 与快捷方式，运行数据保持在独立目录。

## 2. 前后端通信、进程模型与配置

Dashboard 经 127.0.0.1:<selected-port> 调用 API。服务身份接口用于声明应用名、版本和运行来源；模块接口用于核对官方模块版本、兼容范围和包来源。公开资料接口只提供受控 payload。配置模型将消息文件、profile、状态、锁和工件路径以配置文件相对路径解析，默认落在 data 下；多账号场景将受管浏览器资料置于相应账号目录。这样程序目录可在 MSI 更新时替换，而数据目录无需迁移。

任务处理保持明确状态：scheduled 表示等待；running 表示已取得执行路径；retry_pending 表示已证明安全的延迟重试；recovered/completed 表示恢复或完成；final_failed 表示安全重试耗尽；uncertain 表示无法证明未发送；cancelled 表示人为停止。已解决历史依赖同稳定目标的后续权威成功，且之后不能出现更新失败。该规则避免将失败简单隐藏。

## 3. 启动、身份验证与端口选择

托盘以项目根派生本地互斥体。若互斥体已存在，新启动请求交给既有托盘；若不存在，托盘先读取持久化端口，再按持久化值、8765、8766 至 8799 的顺序查看监听者。每个监听者先读取 service identity 和模块信息，再结合 PID、当前 Windows 用户、应用版本、项目/包路径和 Python 解释器判断是否属于本安装。

~~~mermaid
flowchart TD
  A[启动托盘或打开管理台] --> B{单实例互斥体可取得?}
  B -- 否 --> C[请求既有托盘打开已验证页面]
  B -- 是 --> D[读取持久化端口]
  D --> E[探测候选监听者和身份]
  E --> F{健康且身份完全匹配?}
  F -- 是 --> G[复用同端口同 PID]
  F -- 否，已验证旧服务 --> H[仅停止受管理服务]
  F -- 否或无监听 --> I[8765 至 8799 查找空闲端口]
  H --> I
  I --> J[启动本机 CLI UI]
  J --> K[再次验证并保存端口]
  G --> L[打开本机 Dashboard]
  K --> L
~~~

该流程的失败分支非常重要：身份不匹配的监听者不被停止；8765 被无关程序占用时，AutoDy 选择 8766–8799；候选全满时报告错误，不通过抢占端口恢复。已实现并验证的测试表明，无关监听者会保持存活，重复启动会复用同一 AutoDy PID。

## 4. 浏览器隔离、安全恢复与日志

浏览器层在全局锁下运行。会话必须通过稳定身份与显示信息共同验证，之后才进入重复保护和确认。发送前可证明安全的故障才允许写为 retry_pending；可能已发送、确认失败、身份歧义、草稿、附件或清理异常必须停止为 uncertain 或相应终态。Test Center 是可选设置模块，不应成为核心安全链路依赖。

日志用于状态和诊断，但不得充当资料导出渠道。公共 API、备份和诊断导出排除浏览器 profile、Cookie、头像缓存和消息正文。运行时目录不进入 Git 或发布包；发布失败时 CI 保留经控制的隐私诊断，方便定位 allowlist/路径问题。

## 5. 安装器、升级、修复和卸载

WiX 的 INSTALLFOLDER 保存程序文件。新安装先检索有效已登记目录；没有有效旧目录时，D: 可用则优先 D:\AutoDy，否则使用 %LocalAppData%\Programs\AutoDy。AUTODYDATAROOT 始终指向 %LocalAppData%\AutoDy。安装器记录实际路径，修复和升级复用有效路径，陈旧登记路径被拒绝。开始菜单包含打开管理台与卸载快捷方式。

~~~mermaid
flowchart TD
  A[MSI 请求] --> B{有效登记程序目录?}
  B -- 是 --> C[升级或 Repair 复用目录]
  B -- 否 --> D{D: 可用?}
  D -- 是 --> E[D:\AutoDy 新安装]
  D -- 否 --> F[%LocalAppData%\Programs\AutoDy]
  C --> G[部署固定运行时和程序 payload]
  E --> G
  F --> G
  G --> H[数据始终在 %LocalAppData%\AutoDy]
  H --> I{维护操作}
  I -- Repair --> J[恢复程序与快捷方式]
  I -- Upgrade --> K[替换程序，保留数据]
  I -- Uninstall --> L[移除程序/快捷方式，默认保留数据]
~~~

既有 MSI 生命周期验证覆盖安装、修复、v1.4.1 升级、卸载快捷方式和运行时数据保留；1.4.3 本轮对新的 per-machine 原用户身份语义执行本地构建与结构验证，不发布产物。D3DCompiler_47.dll 已验证在 payload 中。当前限制是 MSI 未声称代码签名，且 1.4.3 尚未创建标签或 GitHub Release。

## 6. 发布架构、扩展边界与技术债

Release 只从明确 allowlist 复制文件，使用固定依赖、确定性排序/时间戳和 SHA-256。发行物检查验证 manifest、路径、版本、模块 ZIP 和隐私规则；可重复性测试已通过字节级比较。portable 与 MSI 不是同一安装模型：portable 需要 Python/网络，MSI 带固定运行时。

v1.5 的扩展边界仅是规划：签名与证书运维、更多 Windows/代理/安全软件兼容矩阵、经过安全评审的浏览器适配、以及更广的本机服务发现。当前技术债包括页面变化带来的自动化不确定性、有限端口范围、未签名安装器提示和最终 CI 门禁；这些限制必须显式保留，不能被文档美化为“已解决”。

## 7. 关键接口与失败路径说明

服务身份接口是启动协调协议的一部分，而不是仅供页面展示的版本文本。托盘在 HTTP 探测成功后仍需验证进程所有者和本地路径；反过来，即使某 PID 的命令行看似 Python，也不能绕过 HTTP 身份校验。该双重检查降低旧安装、错误虚拟环境和无关开发服务被误认的概率。模块信息参与核对的目的是防止核心服务正确而捆绑模块来源过期时被静默复用。

端口状态文件只记录候选端口，不是永久信任票据。启动时优先读取它可以减少每次都从 8765 开始的干扰，但每次仍须重新探测监听者并验证身份。若持久端口被无关服务占用，流程回到候选扫描；若该端口上的 AutoDy 身份与当前安装不匹配，流程拒绝附着。这个设计把“可恢复的便利状态”和“安全归属证明”分开。

安装器的登记目录也是同一原则：登记值只是寻找旧安装的线索。WiX 搜索到路径后，后续维护逻辑应确认目录仍为有效 AutoDy payload。拒绝陈旧路径比向其中补写文件更安全，因为后者可能覆盖用户已转换用途的目录或留下双份程序。提升前捕获的原交互用户 SID 和 LocalAppData 是数据根与任务 Principal 的权威输入；提升后的管理员进程环境不得用于推断它们。因此即使用户选择 D:\AutoDy，用户数据仍位于原交互用户的 %LocalAppData%\AutoDy。

错误恢复分为三类。可重试的内部前置失败由任务状态机持久化；可诊断的环境失败如端口、登录或安装路径由托盘/安装器给出明确错误；不可证明安全的浏览器结果被保留为 uncertain。三类都不允许通过“自动继续”跨越安全边界。日志只记录足以定位类别和阶段的信息，敏感资料由导出、备份和发布排除规则保护。

## 8. 设计取舍

系统选择本机单服务而非多个并行服务，是因为浏览器资料、端口和任务锁需要单一协调者。该取舍降低了并发吞吐量，却避免多个窗口竞争同一浏览器或分别解释同一历史。系统选择持久化端口而非每次固定 8765，是为了使安全回退可被后续启动发现；同时又每次重新验证，以避免状态文件成为错误信任来源。系统选择让卸载保留数据而非彻底清理，是为了将程序维护与用户数据删除分离，减少不可逆误操作。

这些取舍的代价是需要更多诊断信息和更清晰的用户提示：用户可能看到非 8765 地址、Repair 不会清空历史、未知监听者不会被自动终止。文档和托盘必须解释这些结果是安全行为，而不是要求用户用危险手段恢复所谓默认状态。

设计审查还应确认每个跨层字段只有一个权威来源：版本来自当前安装元数据，端口来自已验证监听者，安装目录来自有效登记与实际 payload，任务终态来自状态机。若前端、托盘和安装器各自猜测这些字段，会再次引入旧安装或陈旧状态问题。
