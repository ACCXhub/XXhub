# AutoDy 测试计划与测试用例说明

## 1. 目的

本计划定义 AutoDy 的测试层次、环境、准入/退出条件、代表性用例和需求追踪。它回答“应该怎样验证”；实际执行结果、版本和已知失败记录在 09《测试与验收报告》。

测试目标不是追求最大测试数量，而是按风险证明关键契约：不会误发、不会重复发送、不会误伤无关进程、不会丢 DataRoot、不会把私密运行数据带入发布包，并且正常功能可用。

## 2. 测试原则

1. 默认使用单元/集成夹具，不读取真实账号、真实消息、Cookie、browser profile 或备份。
2. 浏览器相关测试优先 mock/fixture/read-only；真实环境验证不得向消息编辑器写入或发送消息。
3. `uncertain`、identity mismatch、未知 PID/端口等 fail-closed 是正确结果，不应为了让测试“成功”放宽。
4. 文档、小展示改动只做相关验证；Installer/Scheduler/send/binding/release 等高风险改动恢复对应聚焦门禁。
5. Release 测试必须绑定同一源码 SHA/标签/构建产物；不同候选的结果不能拼接成一次验收。

## 3. 测试层次

| 层 | 范围 | 主要工具/文件 |
| --- | --- | --- |
| L1 单元 | config、state、failure、retry、binding、account、message、statistics | pytest `tests/test_*.py` |
| L2 领域集成 | runner+chat、discovery+binding、account switching、scheduler service、transfer | pytest |
| L3 API | FastAPI 请求模型、状态码、副作用、投影一致性 | `test_web_api.py` |
| L4 前端 | 页面渲染、交互、异步状态、API contract | Vitest/React tests |
| L5 Windows 脚本/打包 | PowerShell parsing、tray/watchdog、Scheduler、WiX/Portable contract | pytest + PowerShell |
| L6 Release build | portable/MSI 字节可重复性、clean source 构建 | `release_build` marker |
| L7 Windows lifecycle | fresh/repair/uninstall/custom path/upgrade/data retention | `verify-msi-lifecycle.ps1` |
| L8 发布验收 | privacy/package、manifest、public asset re-download/hash | Release workflow |

## 4. CI 与 Release 分层

当前普通 push/PR CI：

- 常规 Python 测试，当前 selection 基线为 **529** 项；
- frontend test suite；
- PowerShell scripts 解析。

正式 Release 执行：

- tag clean-source standalone Portable/MSI；
- privacy/package verifier；
- Windows lifecycle 诊断与报告保留；
- 长时 `release_build` marker 保留给专门诊断，不属于当前 publication gate；
- guarded manifest；
- GitHub Release publish；
- 公开资产重新下载和 hash/MSI/privacy 再验证。

普通 CI 不重复构建数百 MB release artifacts；Release 不把“普通 CI 是否刚跑过”当作替代 clean-source release proof。

## 5. 测试环境

### 5.1 开发/普通 CI

- Windows runner 或开发 Windows 环境；
- Python 3.11 测试环境；
- Node 22 当前 CI；
- 固定 dev requirements / frontend lockfile；
- 运行数据使用测试 tmp_path/fixture。

### 5.2 Release

- GitHub hosted clean Windows runner；
- immutable tag checkout；
- 固定上一稳定 MSI baseline + SHA-256；
- clean source bootstrap；
- 固定 standalone runtime、Chromium、WiX toolchain；
- lifecycle 用户配置必须不存在已有 AutoDy 注册、ProgramRoot、DataRoot 或三项 Scheduler tasks。

## 6. 准入与退出条件

### 6.1 普通变更

准入：Delta 和 owner 明确；相关 fixture 可执行。退出：聚焦测试通过、差异无格式问题、普通 CI 无相关回归。

### 6.2 Release

准入：版本/标签/源码 SHA/Release workflow 一致；上一稳定资产 hash 可验证；工作树状态已收敛。退出：canonical build、privacy/package、manifest、publish、public reverify 全绿；lifecycle 诊断报告按 workflow 保留。

任何 blocker 未关闭即为“候选失败”，不能把部分通过写成完整验收。

## 7. 核心测试用例

| Case | 前置条件/操作 | 预期 |
| --- | --- | --- |
| TC-CFG-01 | 读取/保存合法 config | 路径解析一致、原子保存、字段约束保持 |
| TC-CFG-02 | 重复 stable_id/candidate_id 或非法 delay/deadline | 模型拒绝，不写入 |
| TC-BIND-01 | 完整 discovery + 唯一权威 identity + 同账号 | resolver 返回 valid/current locator |
| TC-BIND-02 | 仅名称/头像匹配、identity 缺失 | 不建立 durable proof |
| TC-BIND-03 | candidate 已被其他 Target 占用 | relink 409，不改变 binding |
| TC-BIND-04 | logout/revalidation guard 存在 | Runner 不把旧 binding 当健康 |
| TC-DISC-01 | 虚拟列表继续 lazy-load | 扫描等待增长并收敛完整候选 |
| TC-DISC-02 | 扫描失败/取消 | 上次有效 cache/binding 不被空结果破坏 |
| TC-SEND-01 | stable binding + unique conversation + 空 composer | 发送一次并进入 confirmed/completed |
| TC-SEND-02 | 已有同日成功 | 不重复发送 |
| TC-SEND-03 | 发送前页面/会话失败，send_attempts=0 | 可进入 safe retry（受次数/截止时间限制） |
| TC-SEND-04 | 发送已尝试但确认失败 | `uncertain`，自动重试不可用 |
| TC-PREF-01 | 运行 preflight | 只打开会话/读取 DOM，fill/type/press/send 计数均为 0 |
| TC-ACC-01 | 无浏览器任务时切换账号 | snapshot 当前 runtime，恢复目标账号，binding/account scope 一致 |
| TC-ACC-02 | send/dry-run/browser action 正在执行 | account switch/add/logout 409 |
| TC-ACC-03 | legacy migration 中途失败 | config/browser profile 回滚 |
| TC-HIST-01 | 追加多个 TaskRunRecord | JSONL 追加、分页/过滤正确 |
| TC-HIST-02 | 后续权威成功 | 旧失败保留但可标 resolved，不删除历史 |
| TC-SCH-01 | Scheduler 返回成功空列表 | 明确表示 0 项任务 |
| TC-SCH-02 | Scheduler timeout/PowerShell/JSON 失败 | 显式 read error，不折叠为 0 |
| TC-SCH-03 | Dashboard 应用计划 | 仅单次 UAC 写任务，Principal=原用户、RunLevel Limited |
| TC-TRAY-01 | 8765 被无关服务占用 | 无关 PID 存活，AutoDy 选 8766–8799 |
| TC-TRAY-02 | 已有同 installation AutoDy 服务 | 重复启动复用已验证 PID |
| TC-WD-01 | 受管服务进程退出 | watchdog 有界自动重启 |
| TC-WD-02 | 进程存在、health 短暂失败 | 未满连续约 15–20s 不判 hung |
| TC-WD-03 | 需要强停 | graceful 失败后重新验证 exact PID，不能按名称批杀 |
| TC-WD-04 | 10 分钟第 4 次恢复 | 熔断/needs-attention，不继续重启 |
| TC-WD-05 | 用户显式完整退出 | 同日自动恢复被抑制 |
| TC-BACK-01 | 创建 v2 backup | manifest/checksum/类别正确，browser profile 不包含 |
| TC-BACK-02 | invalid backup / 写入失败 | 拒绝或恢复原 config/messages |
| TC-LOG-01 | diagnostic export | 只有 masked summary；排除消息/Cookie/profile/avatar/discovery |
| TC-MSI-01 | fresh install | payload/快捷方式/三任务存在，DataRoot 属原用户 |
| TC-MSI-02 | Repair | payload/快捷方式/任务恢复，DataRoot 不丢 |
| TC-MSI-03 | default uninstall | 产品注册/ProgramRoot/tasks 删除，DataRoot 保留 |
| TC-MSI-04 | custom install/uninstall | payload 只在选定目录，卸载无程序残留 |
| TC-MSI-05 | v1.4.4→current migration/upgrade | 旧注册处理、DataRoot 保留、current 产品与任务正确 |
| TC-REL-01 | 同输入两次 portable/MSI build | 字节/identity 可重复 |
| TC-REL-02 | privacy/package verify | allowlist/manifest/CAB/DLL/CustomAction/私密扫描通过 |
| TC-REL-03 | publish 后重新下载 | 文件集合与 manifest/hash 一致 |

## 8. 前端验收要点

- Dashboard 的今日总数、好友状态行/标题与资源统计来自同一 executable Target set。
- Friends enable/disable/relink 后刷新状态必须收敛，不显示两个互相矛盾的 owner。
- async action 只能有一个清晰主状态/动作；错误后不自动重复提交。
- `uncertain` 不展示自动补发；binding 问题进入 Friends，账号问题进入登录/切换。
- 好友状态列表自然展开，不用内部滚动隐藏当前行。
- 常用笔记本尺寸不能出现破坏主流程的横向溢出。

## 10. 缺陷分级

**Release blocker**：误发/重复发送风险、unknown PID 被停止、DataRoot 丢失、认证/私密数据进包、MSI 生命周期失败、公开资产 hash 不一致。

**高优先级**：Scheduler drift、绑定错误、账号隔离失败、Repair/卸载残留会影响下一次运行。

**普通缺陷**：不改变业务事实和安全边界的展示/文案/低影响交互问题。

修复 blocker 时只定位失败阶段并运行对应 focused validation；除正式 Release 外不重复完整重型构建。

## 11. 测试证据管理

实际证据引用命令摘要、CI run、release report、manifest/hash 或测试结果。诊断文件保留最小必要内容；失败生命周期报告应在 workflow 中可上传/获取，避免只留下“verification failed”而丢失具体 stage/failure。
