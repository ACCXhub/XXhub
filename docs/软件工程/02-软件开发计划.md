# AutoDy 软件开发计划

## 1. 计划目的

本计划定义 AutoDy 当前维护线的开发、变更、配置、测试、文档与发布方式。它描述长期有效的工程流程，不复制每次临时任务的实施清单；具体历史设计与阶段计划完成后归档到 `docs/archive/`。

当前项目目标是维护已有 Windows 本机产品，优先处理可靠性、安全、安装和发布阻断问题。新工作必须以现有 canonical owner 为起点，避免通过平行脚本、平行状态文件或重复文档解决局部症状。

## 2. 生命周期与里程碑

AutoDy 已经历以下可识别阶段：

1. **本地工作流基础**：Dashboard、目标、文案、Scheduler、运行历史和受管浏览器。
2. **安全发送与可诊断状态**：稳定目标身份、重复保护、确认、失败分类、只读 preflight、日志与备份。
3. **Windows 产品化**：托盘、动态端口、service identity、MSI/Portable、ProgramRoot/DataRoot 分离。
4. **安装与权限加固**：per-machine MSI、原交互用户 SID/DataRoot、Limited Scheduler、受约束 UAC、Repair/卸载/升级。
5. **v1.5.0 可靠性候选**：watchdog、服务生命周期、稳定好友 binding/reassociation、多账号隔离、Friends/Overview 一致性和 CI/Release 分层。
6. **当前发布收口**：保留失败的 v1.5.0/v1.5.1 tag 历史，在新 v1.5.2 身份上完成正式 GitHub Release；之后进入维护期。

里程碑完成的定义不是“代码写完”，而是相应需求、实现、聚焦验证和必要文档均收敛；Release 里程碑还要求公开资产与 hash/manifest 一致。

## 4. 变更流程

### 4.1 任务锚点

每项变更先明确五个事实：Outcome、Master、Locked、Delta、Deliverables。当前最优已验收状态是 Master；新改动只改变 Delta，不因“最新”而自动成为 Master。

### 4.2 实施原则

- 修改责任的 canonical owner，不复制同一业务逻辑到第二个模块。
- 只有已有明确复用场景且边界稳定的能力才上提共享层。
- 失败应回到根因和 owner；不在退化结果上层层补丁。
- 临时 staging、诊断和构建目录属于可再生成工作产物，完成后按脚本策略收敛，不充当版本历史。
- 对用户数据和不可逆操作使用明确路径/身份验证；不以端口、进程名、昵称或头像作为唯一归属证明。

## 5. 配置管理

### 5.1 Git

- `main` 是当前 canonical 开发线。
- Git 保存历史；当前文档与代码原位更新，不创建 `final/fixed/latest` 副本。
- 已发布标签和 Release 资产视为不可变历史。未成功发布的候选标签如需调整，必须作为独立发布决策处理，不能在文档任务中顺手移动。
- `output/`、运行 DataRoot、`.venv`、`node_modules`、浏览器资料、日志和缓存不进入源码版本控制。

### 5.2 版本事实

版本同时存在于源码元数据、前端元数据、构建/Release workflow 和发布文档时，必须保持一致。版本字符串更新不代表 Release 已完成；对外稳定状态只由已成功发布并通过验收的公开资产确定。

## 6. 测试策略

普通开发 CI 与正式 Release validation 分离：

- **push/PR**：常规 Python 测试（当前选择 529 项）、frontend tests、PowerShell 解析。
- **Release**：额外运行标记为 `release_build` 的大型可重复性测试（当前 2 项），再执行 standalone portable/MSI 构建、privacy/package verifier、Windows MSI lifecycle acceptance、manifest、发布和公开资产再校验。

日常修改只运行与 Delta 直接相关的聚焦测试，再由普通 CI 承担回归；不因为文档/小改动本地重复构建数百 MB 的 MSI。安装器、托盘、Scheduler、安全发送等高风险边界必须恢复对应聚焦或 Release 验证。

测试详细准入、用例与追踪见 08；实际结果见 09。

## 7. 发布计划

正式版本发布顺序：

1. `main` 收敛，版本/文档/Release workflow 一致；
2. 必要的 focused validation 完成；
3. 创建目标版本 tag；
4. Release workflow 验证历史标签与上一稳定 MSI baseline；
5. 从该 tag 的 clean source 执行重型 release tests 和 standalone 构建；
6. 执行 privacy/package 与 MSI lifecycle acceptance；
7. 生成 guarded release manifest；
8. 上传 canonical MSI、checksum、Portable、checksum、manifest；
9. 重新下载公开资产，校验文件集合、hash、MSI/隐私；
10. workflow 全绿后才把该版本称为正式稳定 Release。

任何 blocker 应只修对应 owner，然后产生新的最终 release source；不得用手工上传绕过已定义的正式门禁后仍宣称“完整验收”。若业务决定降低门禁，必须先修改本计划/08 和 Release workflow，使验收定义显式改变。

## 9. 风险管理

高风险变更包括：发送身份、`uncertain`/retry、浏览器锁、账号切换、服务 PID 终止、Scheduler Principal、ProgramRoot/DataRoot、MSI lifecycle、备份导入和隐私 allowlist。此类改动必须有明确失败路径和聚焦回归；若验收无法证明安全，产品行为应停止而不是自动猜测。

中低风险变更包括纯展示、文案和不改变契约的内部整理，按影响范围验证即可。测试数量由风险决定，不以“跑得越多越安全”为目标。

当前项目完整交付物包括：

- guarded release manifest；
- README/CHANGELOG/RELEASE_NOTES/SECURITY/第三方说明；
- 本目录 00–13 软件工程文档；
- 测试源码与 Release workflow 证据；

v1.5.2 的交付物只有在 source/build、MSI/Portable、privacy/package、manifest、公开资产校验和本地安装验收完成后才视为正式发布完成；hosted-runner lifecycle 作为非阻断诊断保留。
