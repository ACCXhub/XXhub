# AutoDy 项目交接说明

## 1. 当前状态

当前分支为 main，核心版本为 1.4.3。v1.4.3 是已验证稳定源码基线，尚未创建标签或 GitHub Release；本地 MSI 仅用于冻结验证，不是公开发布资产。v1.4.0、v1.4.1 已存在且不可移动。官方 Test Center 为 1.2.0，模块 API 为 1，兼容 >=1.3.0,<2.0.0。

## 2. 仓库与核心模块

src/autody 承载 FastAPI、配置、状态、历史、浏览器安全和模块；frontend 为 React/Vite Dashboard；scripts 包含 bootstrap、托盘、构建和验证；packaging/wix 为 WiX 定义；tests 覆盖 API、托盘、打包与发布；docs 是中文工程交付资料。output、data、.venv、node_modules、日志、缓存和浏览器资料均是运行时/构建边界，不能提交或删除。

重要入口包括服务身份 API、配置模型、PowerShell 托盘、MSI 构建、Release artifact 验证、WiX Product 定义和生命周期脚本。修改这些位置时，应同时阅读 01 至 06 对应章节，避免代码、测试与文档表述分离。

## 3. 已完成的 v1.4.3 工作

已实现并验证：历史 Dashboard 统计使用各历史日期自己的目标与结果事实，后续配置变化不会追溯改写过去；缺失日不计入成功率分母但中断连续成功。Dashboard 不再重复呈现逐次历史，详细历史留在日志页；好友管理移除单项删除并保留整行启停、重新关联、忽略和全量删除。文案包以安装内置文件为唯一来源。

已实现并验证：Scheduler 修复显式接收 ProgramRoot、DataRoot 与目标用户 SID，并在注册后验证全部任务；MSI 使用 per-machine 语义，提升前捕获原交互用户 SID 与 LocalAppData，首次种下但不覆盖 config.yaml。新 MSI 仍优先 D:\AutoDy、回退原交互用户的 %LocalAppData%\Programs\AutoDy，并保持程序/数据目录分离和卸载数据保留。

已实现并验证：非提升 Dashboard 的 Scheduler 安装、修复、移除和应用设置使用一次性 UAC 子进程，并继续调用既有任务脚本；原进程 SID、ProgramRoot 与 DataRoot 显式跨越提升边界。真实安装 UI 已完成移除后恢复和计划设置变更后恢复，最终三项任务 Ready、Limited、原用户 Principal、正确 roots 且 0 drift。

已实现并验证：MSI 与 portable 共用受控 runtime staging，二者均携带固定 Python、native 扩展、Chromium、生产前端、文案包和官方模块。`runtime/distribution-mode.txt` 与 `resolve-runtime-roots.ps1` 统一解释 ProgramRoot、DataRoot、Python 和 BrowserRoot；portable 通过 `AutoDy.cmd` 启动并把数据留在解包目录。文本规范化为 PowerShell 脚本保留 UTF-8 BOM，同时保持 VBS 的 Windows Script Host 兼容编码。MSI 普通卸载在删除程序文件前调用既有 `remove-task.ps1`，防止留下悬空任务，同时保持 DataRoot。最终 Portable 实际启动与 MSI 安装、Repair、卸载、重装均通过；没有创建或上传发行物。

## 4. 本地开发、构建、测试与发布

开发使用项目 .venv；产品改动后按需求运行 doctor、Python 测试、前端测试/构建、portable/MSI 构建和发行物验证。文档任务不应重装 AutoDy 或运行 MSI 生命周期。完整发布需在干净源码和干净 Windows 用户配置中，以已验证旧 per-user MSI 作为迁移基线，执行“卸载旧程序、保留 DataRoot、安装 per-machine 1.4.3”，再运行生命周期和发布验证并触发一次最终 Release CI。

本地构建已用于核验 1.4.3 MSI、Portable、SHA-256、standalone payload、allowlist、隐私报告和真实 Windows 生命周期，但没有上传任何产物。若未来决定正式发布，仍需从对应 clean commit 重新走发布门禁；本任务不创建标签、Release 或 PR。禁止 force-push、移动旧标签或以本地结果替代正式发布门禁。

## 5. 运行时、隐私和常见错误

任何真实账号、目标、消息、Cookie、令牌、浏览器 profile、头像、备份、日志或模块注册表都不得读出、打印、提交或作为夹具。服务端口和 PID 不足以证明归属；先确认 service identity、用户、路径和解释器。不要按进程名杀 Python、PowerShell、Chrome 或 Edge。不要用删除 data、浏览器资料或仓库的方式解决登录、端口或安装问题。

## 6. 接手后的第一小时

1. 阅读 AGENTS、文档总览、本交接和最新 Git 状态。
2. 执行 git status、git log -8 和 git remote -v，保留所有未提交工作。
3. 确认版本、标签和 Release 状态；v1.4.3 仍不能发布。
4. 针对当前任务仅读取必要代码，先找测试或已有验证证据。
5. 涉及 8765 时先验证服务归属，不停止无关监听者。
6. 涉及浏览器时只用夹具或只读路径，不触碰真实编辑器。
7. 变更发布、路径、数据或隐私逻辑时同步更新中文文档并运行相应检查。
8. 提交前运行 git diff --check；发布前等待一次最终 CI。

## 7. 限制与 v1.5 待规划事项

当前限制是本机单机范围、浏览器页面变化、未签名 MSI、有限端口范围和最终 CI 未完成。v1.5 待规划而非已实现的事项包括代码签名、证书治理、更广 Windows/代理/安全软件矩阵、更多浏览器适配和扩展服务发现。任何此类工作必须重新评估身份、去重、不确定状态和数据边界。

## 8. 变更决策与审查建议

修改前先写出要证明的事实：例如“现有服务是否属于当前安装”“该安装目录是否仍有效”“失败是否发生在任何发送动作之前”。然后选择对应的代码、测试或既有验证证据。不要用“页面看起来正常”替代服务身份验证，也不要用“测试没报错”替代检查实际候选包和数据保留。

审查文档或代码时重点检查四个边界：程序目录与数据目录是否混淆；端口与进程是否被当作唯一身份；诊断是否可能泄露运行时资料；新自动化是否错误跨过 uncertain、草稿或身份不一致状态。出现这些问题时，应优先缩小行为和明确失败，而不是增加隐式重试或删除资料的“自愈”。

本任务完成后，长期工程文档以中文路径为准。英文 AUTODY_ENGINEERING_MANUAL、PROJECT_HANDOFF 和 RELEASE_NOTES 仅是构建、发布或既有规则的兼容入口；不要重新向它们复制长篇内容。任何新文档先评估是否能合入现有八份，而不是创建内容重叠的独立说明。

## 9. 发布前的最小复核清单

确认工作树只含预期文件；确认版本、标签和候选目录未混用；确认 MSI/portable/hash/manifest 同属一个提交；确认隐私扫描、打包检查和生命周期证据可追溯；最后触发一次 Release CI。CI 通过前，所有候选都保持未发布状态。若任一项缺失，应回到对应构建或验证阶段，而不是创建临时标签或发布后补证据。

接手者若只处理文档，应限制验证为链接、围栏、敏感路径、差异和必要的文档测试；不要因为看到发布脚本就重新安装或清理环境。接手者若处理代码，则先恢复本文件列出的对应验证层级，并在提交说明中写清是否影响服务身份、数据保留、端口或发布包。

## 10. 常见误区

不要把当前候选版本写成已发布；不要因为主分支存在候选提交就移动标签；不要把本地 8765 监听者自动视为 AutoDy；不要把 portable 当成需要开发环境的源码包；不要把卸载保留 DataRoot 当成卸载失败，也不要把卸载后遗留 Windows 任务当成正常保留；不要将数据目录、日志或 profile 纳入 Git。上述错误大多来自把便利状态当作权威事实，接手时应以服务身份、manifest、测试记录和正式 CI 为准。
