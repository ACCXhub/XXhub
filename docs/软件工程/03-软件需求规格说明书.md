# AutoDy 软件需求规格说明书

## 1. 目的与范围

AutoDy 是 Windows 本机运行的 Douyin 私信工作流管理台。系统管理续火目标、文案、计划、运行状态、历史、日志、备份、受管浏览器和本机安装生命周期，并以“不能证明安全就停止”为核心可靠性原则。

本需求说明面向当前 1.5.1 代码线。`v1.5.0` 是 lifecycle 失败且未发布资产的历史标签；v1.5.1 只有在正式 Release workflow 和公开资产再校验全绿后才视为稳定发布。

范围内：本地 Dashboard、受管浏览器、目标与好友发现、稳定绑定、消息与文案包、Scheduler、发送前自检、发送状态机、账号隔离、日志与备份、托盘/watchdog、MSI/Portable 和正式 Release validation。

范围外：云端多租户、远程控制、验证码/登录绕过、未知网站通用自动化、绕过平台规则、把真实浏览器资料或消息上传到公共服务。

## 2. 用户与运行假设

- 普通用户：在自己的 Windows 账户中安装/运行 AutoDy，通过受管 Chromium 登录 Douyin。
- 维护者：诊断本机服务、Scheduler、安装器、发布包和安全边界。
- 发布维护者：从 Git tag 触发正式 Release workflow，并只发布通过门禁的 canonical assets。

系统默认只监听 `127.0.0.1:<selected-port>`。用户数据属于原交互 Windows 用户；MSI ProgramRoot 与 DataRoot 分离，Portable 的 ProgramRoot/DataRoot 都位于解包目录但仍由统一 resolver 定义。

## 3. 功能需求

| ID | 需求 | 失败/安全行为 | 主要验证 |
| --- | --- | --- | --- |
| FR-001 | Dashboard 展示当前健康、今日任务、好友状态、计划、历史和需处理事项。 | API 不可用或资料不确定时显示可诊断状态，不伪造成功。 | `test_web_api.py`、frontend tests |
| FR-002 | 用户可维护目标、文案、文案包、全局/目标级设置。 | 写入必须经过模型/业务约束；并发或 revision 冲突明确拒绝。 | config/message pack/API tests |
| FR-003 | Windows Scheduler 按配置执行每日健康检查、每日续火和每周健康检查。 | 计划漂移、UAC 取消、读取失败必须显式报告；Dashboard 不永久提升。 | scheduler tests、lifecycle |
| FR-004 | 自动执行前使用稳定 Target 身份、账号范围和当前 discovery 解析目标。 | 昵称、头像或弱 locator 不能单独升级为 durable proof；歧义时阻止。 | binding/discovery/runner tests |
| FR-005 | 发送动作必须经过会话定位、重复保护、全局 browser lock 与确认。 | 身份不一致、草稿、附件、页面异常或结果不确定时停止。 | chat/runner tests |
| FR-006 | 只对已证明发生在可能发送动作之前的失败提供有限自动重试。 | `uncertain`、确认失败或可能已发送不得自动重试。 | retry/runner/failure tests |
| FR-007 | 好友发现缓存当前候选、头像、本次扫描完整性和权威 identity 证据。 | 部分/失败/取消/陈旧扫描不能覆盖已有稳定绑定事实。 | friend discovery tests |
| FR-008 | 用户可对 orphan/失效绑定执行显式重新关联。 | 只有完整当前 discovery 中唯一、账号一致、未占用且具有权威 identity 的 candidate 可写回。 | binding recovery/API tests |
| FR-009 | 多账号本地隔离保存账号级目标、计划、浏览器 profile 与运行快照。 | 切换/添加/退出时若有受管发送或浏览器任务，必须拒绝；迁移失败可回滚。 | account profile tests |
| FR-010 | 发送前自检只检查聊天页可发送条件。 | 不选取/写入/发送消息；仅允许打开会话行和读取 DOM。 | preflight tests |
| FR-011 | 运行历史记录 run_id、触发来源、计数、终态、确认和结构化失败。 | 历史失败不能因当前配置或后续 UI 投影被删除；后续成功只能标记解决。 | history/statistics/API tests |
| FR-012 | 日志中心支持筛选、保留、归档和脱敏诊断导出。 | 诊断不得导出消息正文、Cookie、browser profile、头像缓存或好友缓存。 | log center/API tests |
| FR-013 | 备份中心支持选择类别、预览、合并/替换和 legacy v1 导入。 | 导入先验证；失败回滚当前配置/文案；浏览器 profile 不进入普通备份。 | transfer/API tests |
| FR-014 | 托盘提供单实例、服务发现、动态端口、打开/重启/退出入口。 | 端口/PID 本身不证明归属；未知监听者不附着、不停止。 | tray/service-recovery tests |
| FR-015 | watchdog 自动恢复已确认属于 AutoDy 的异常本机服务。 | 进程存活时需连续 health 失败约 15–20 秒才判 hung；先正常退出，必要时只终止重新验证过的具体 PID；10 分钟最多 3 次自动恢复，之后进入需处理；用户明确完整退出抑制同日自动恢复。 | watchdog/service recovery tests |
| FR-016 | watchdog 恢复只负责服务生命周期。 | 自动恢复不得发送消息、扫描好友、修复 Scheduler 或修改无关 DataRoot。 | watchdog tests/代码边界 |
| FR-017 | MSI 支持新装、Repair、升级、卸载、自定义 ProgramRoot；默认保留 DataRoot。 | 不允许未知平行目录、删除用户 DataRoot、遗留指向已删除 ProgramRoot 的 AutoDy 任务。 | MSI packaging + lifecycle |
| FR-018 | Portable 提供 standalone Python、依赖、Chromium、前端与资源。 | 不依赖系统 Python/Node/npm/源码仓库或在线恢复依赖。 | portable/release tests |
| FR-019 | 正式 Release 从 immutable tag 的 clean source 构建并验证。 | lifecycle/privacy/hash/manifest 任一阻断时不发布公开资产。 | Release workflow |

## 4. 非功能需求

### NFR-001 本地性

业务服务只绑定 loopback。产品运行不要求云端数据库或 AutoDy 自有远程后端。

### NFR-002 可维护性

每项责任有唯一 canonical owner；路径通过共享 runtime/root resolver 与配置模型解释。配置/状态写入优先采用临时文件 + replace 等原子更新方式。

### NFR-003 可诊断性

关键失败提供阶段、原因码和安全动作；服务身份、selected port、Scheduler drift、安装日志、Release report 都应能定位到具体 owner，而非只显示“失败”。

### NFR-004 兼容性

当前目标平台为 Windows x64；源码要求 Python 3.11+。正式 MSI/Portable 包含固定运行时，降低对用户系统开发环境的依赖。

### NFR-005 性能

Dashboard 常规读取不应触发真实浏览器扫描或 release 构建。好友 targeted refresh 与完整 discovery 分离；缓存具有明确 TTL。重型 reproducibility/MSI tests 只在正式 Release 执行。

### NFR-006 可恢复性

服务、Scheduler、安装器和账号切换都应区分“可安全恢复”与“状态未知”。恢复不能通过删除数据、猜测服务或重试 uncertain 来获得表面成功。

## 5. 可靠性需求

- REL-001：所有真实浏览器任务共享全局锁；账号切换与受管发送互斥。
- REL-002：运行终态至少区分 `already_done/completed/retry_pending/recovered/final_failed/uncertain/cancelled`。
- REL-003：同日成功不重复发送；失败目标只有在安全条件满足时才能目标级补发。
- REL-004：历史日期的成功率/状态不被后来目标配置追溯改写。
- REL-005：服务 health 暂时失败不能立即触发强制恢复；watchdog 有迟滞和熔断。
- REL-006：任务快照查询失败与“成功查询到 0 项任务”是不同状态。
- REL-007：Release 候选的源码 SHA、构建、manifest、hash 和公开资产必须属于同一候选。

## 6. 安全与隐私需求

- SEC-001：发送前身份、账号范围、重复保护、确认和 browser lock 优先于便利性。
- SEC-002：未知进程/端口监听者保持不受 AutoDy 影响；不能按 `python.exe` 名称或端口批量结束进程。
- SEC-003：Cookie、令牌、browser profile、真实账号/好友/消息不得进入 Git、发布包、文档和普通诊断。
- SEC-004：Scheduler 使用原交互用户 Principal 和 `RunLevel Limited`；Dashboard 常态非提升，写操作使用受约束短生命周期 UAC。
- SEC-005：普通卸载默认保留 DataRoot；永久删除用户数据必须是独立、明确且路径已确认的动作。
- SEC-006：备份与诊断采用 allowlist/类别选择，不把本机运行目录整体打包。
- SEC-007：无权威 friend proof、账号不一致、扫描不完整或匹配不唯一时绑定解析 fail closed。

## 7. 安装与发布需求

- INS-001：MSI ProgramRoot 与原交互用户 `%LocalAppData%\AutoDy` DataRoot 分离。
- INS-002：新装默认优先 `D:\AutoDy`，不可用时回退原交互用户 `%LocalAppData%\Programs\AutoDy`，并允许明确的自定义目录。
- INS-003：Repair 恢复程序 payload/快捷方式/Scheduler 契约，不清空 DataRoot。
- INS-004：普通卸载移除程序、快捷方式和三项 AutoDy Windows Tasks，保留 DataRoot。
- INS-005：1.4.0–1.4.2 per-user 到 1.4.3+ per-machine 的范围迁移按已定义卸载旧登记/保留数据/安装新包流程处理。
- INS-006：正式 Release 必须验证上一稳定 MSI baseline 的固定 SHA-256，再执行当前候选生命周期。

## 8. 验收优先级

当需求冲突时按以下顺序处理：

1. 避免误发送、重复发送和用户数据损失；
2. 不误伤无关进程/账户/安装；
3. 保留可诊断与可恢复现场；
4. 保持计划与运行连续性；
5. 最后才优化点击数、速度与展示便利。

因此，“拒绝执行”“保持 uncertain”“保留 DataRoot”“不结束未知 PID”都可能是正确验收结果。
