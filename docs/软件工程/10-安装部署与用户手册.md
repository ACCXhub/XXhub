# AutoDy 安装部署与用户手册

## 1. 版本说明

本手册描述当前 1.5.2 代码线的安装与使用模型，但下载状态必须按 GitHub Release 事实判断。`v1.5.0`、`v1.5.1` 标签均未完成公开发布；v1.5.2 Release pass 开始前最后已确认稳定基线仍为 **v1.4.4**。

因此：只有当 GitHub `ACCXhub/XXhub` Releases 中真正出现 v1.5.2 MSI/Portable、checksum/manifest 且 Release workflow 全绿后，才按本文的 v1.5.2 文件名执行安装；否则继续使用最后已发布稳定版本。

## 2. 支持环境与分发形式

目标平台为 Windows x64。

- **MSI**：普通用户首选；ProgramRoot 与 DataRoot 分离，Windows Installer 维护安装/Repair/升级/卸载。
- **Portable**：技术用户可选；完整解压后从顶层 `AutoDy.cmd` 启动，程序和数据都留在解包目录。
- **Source**：仅用于开发；需要 `.venv`、Node/frontend 等开发环境。

正式 MSI/Portable 自带固定 Python、依赖、Chromium、生产前端和内置资源，不需要安装系统 Python/Node/npm 或手工 Playwright Chromium。

## 3. 下载与 SHA-256 校验

只从仓库正式 Releases 下载。以目标版本为例：

```powershell
Get-FileHash -Algorithm SHA256 '.\AutoDy-<version>-x64.msi'
```

结果必须与同一 Release 中 `.msi.sha256` 一致。Portable 同理。若版本资产尚不存在、hash 不一致或 Release 仍失败，不要把本地/CI 中间 MSI 当作正式安装包。

## 4. MSI 首次安装

1. 双击已验证 MSI，接受该次 Windows 提升。
2. 安装器在提升前捕获原交互用户 SID 与 LocalAppData，用于 DataRoot 和 Scheduler Principal。
3. 新安装默认优先 `D:\AutoDy`；D: 不可用时回退原交互用户 `%LocalAppData%\Programs\AutoDy`。
4. 如需自定义 ProgramRoot，在安装向导选择明确、可写、专用于 AutoDy 的目录。
5. 完成后从桌面/开始菜单打开 AutoDy。

正常结果：程序 payload 在 ProgramRoot；用户数据在原交互用户 `%LocalAppData%\AutoDy`。两者不能因为安装提升而落到管理员账号的 LocalAppData。

不要把网络共享、其他应用目录、浏览器 profile 目录作为安装位置；遇到陈旧登记路径或安装失败时保留日志，不先删除 DataRoot。

## 5. 首次启动与托盘

快捷方式启动托盘。托盘首先验证已有 AutoDy 服务：service identity、当前用户、ProgramRoot/package path、Python executable 与受管进程信息都匹配才会复用。

首选端口 8765；若被无关程序占用，AutoDy 在 8766–8799 中选择安全空闲端口并可持久化提示。**端口号不是固定入口**，日常应从托盘打开 Dashboard，不手工猜端口。

重复启动正常应复用同一已验证 AutoDy 服务。未知监听者不会被停止；不要通过“结束所有 python.exe”解决端口问题。

## 6. 登录与多账号

登录只在 AutoDy 受管 Chromium 中完成，不复制日常浏览器 Cookie/profile。

当前版本支持本地多账号 profile：切换账号会保存当前账号级目标、计划和 runtime snapshot，再恢复目标账号的 browser profile/数据。真实发送、dry-run 或其他受管 browser action 运行时，添加/切换/退出账号会被拒绝，用户应等待当前操作结束。

退出账号会先把现有 binding 标记为需要重新验证，再清理受管 Douyin 认证；重新登录后必须重新取得账号范围和稳定 binding proof，旧 Target 不因名字相同自动获得信任。

## 7. 好友与重新关联

好友管理中的扫描只读聊天列表并维护本地 candidate/头像缓存。对新候选加入续火或旧 Target 重新关联时，后端必须证明：

- discovery 当前且完整；
- candidate 未被其他 Target 占用；
- 有权威好友 identity；
- account scope 匹配；
- identity 唯一。

如果页面只提供相同昵称/头像、扫描不完整、账号不一致或候选歧义，AutoDy 会要求处理而不是猜测关联。

取消续火会把 Target 移出当前 executable set；重新加入后 Overview 的今日总数、好友状态和资源投影应同步收敛。

## 8. 文案、文案包与计划

- “文案库”维护本地 `messages.txt`，支持 TXT/CSV/JSON 预览/导入/导出和去重。
- “文案包”维护内置/自定义 pack，可设置稳定 ID 的默认 pack，也可为单个 Target 覆盖。
- Target 可配置后缀、延迟、顺序和文案选择方式。
- “定时任务”管理每日健康检查、每日续火和每周健康检查。

Dashboard 常态非管理员。只有安装/修复/移除/应用 Windows Tasks 时出现一次性 UAC；取消 UAC 后当前 Windows Tasks/配置不应被半写入。

## 9. 状态理解

| 状态 | 含义 | 用户动作 |
| --- | --- | --- |
| `already_done` | 当日已完成 | 无需重复运行 |
| `completed` | 当前运行完成 | 查看总览即可 |
| `retry_pending` | 已证明失败发生在可能发送前，等待有界安全重试 | 等待/查看失败详情 |
| `recovered` | 后续安全重试成功 | 无需重复补发 |
| `final_failed` | 安全重试耗尽/超过截止 | 人工查看原因 |
| `uncertain` | 可能已发送或无法确认 | **不要自动/手动重复发送覆盖状态** |
| `cancelled` | 用户/受控流程取消 | 确认现场再决定后续 |

“历史失败已解决”只表示同 stable Target 后续有权威成功，历史记录仍保留。

## 10. 发送前自检

Preflight 可以验证登录、聊天列表、唯一目标、composer 和发送控件是否存在，但它不选消息、不输入、不发送。自检失败只说明当前页面未满足条件；不要把连续点击“自检”当作发送或修复手段。

## 11. Watchdog 与服务恢复

watchdog 只恢复受管本机服务：进程退出可自动重启；进程存在时需 health 连续失败约 15–20 秒才判无响应；先尝试正常退出，强停前重新验证 exact PID。10 分钟最多 3 次自动恢复，之后进入需处理。

用户从托盘执行明确的完整退出后，同日自动恢复被抑制。watchdog 不会因此发送消息、扫描好友或修 Scheduler。

## 12. 日志与备份

日志中心提供筛选、保留、归档和脱敏诊断。向他人提供材料时只使用受控 diagnostic export 或经过人工审查的摘要，不发送完整 DataRoot、浏览器 profile、Cookie、真实消息或好友缓存。

备份中心可选择类别并预览导入；新备份包含 manifest/checksum，普通备份不导出 browser profile。导入前先 preview；不要用手工复制覆盖配置来替代备份导入。

## 13. Repair、升级与卸载

### Repair

用 Windows Installer 的 Repair 恢复 ProgramRoot payload、快捷方式和安装期 Scheduler 契约。Repair 默认不清空 DataRoot。

### 升级

1.4.0–1.4.2 是 per-user；1.4.3 及后续是 per-machine。跨 scope 迁移不能依靠普通 MajorUpgrade 自动发现旧产品：应按产品定义流程正常卸载旧程序登记/ProgramRoot、保留 `%LocalAppData%\AutoDy`，再安装新 MSI。

从 v1.4.4 到正式 v1.5.2 的升级只有在 v1.5.2 Release workflow、公开资产校验和本地安装验收完成后才属于受支持的公开升级路径。workflow 未全绿时不要用未发布 MSI 覆盖稳定安装。

### 卸载

Windows 设置或开始菜单“卸载 AutoDy”应删除：

- 当前 MSI 产品注册；
- ProgramRoot 程序文件；
- 桌面/开始菜单入口；
- 三项 AutoDy Scheduler tasks。

普通卸载默认**保留 DataRoot**，包括配置、历史和受管资料。永久删除数据是另一项独立、明确且不可逆的用户决定。

## 14. Portable

完整解压 `AutoDy-Windows-Portable-<version>.zip` 后运行顶层 `AutoDy.cmd`。不要从 ZIP 内运行或只复制启动脚本。Portable 数据随目录存在；复制目录等于复制其本地资料，删除目录等于删除 Portable 数据。

同机同时存在 MSI/Portable 时，从各自入口启动并核对 service identity，不让不同分发实例并发控制同一个 browser workflow。

## 15. 常见问题

| 症状 | 首先做什么 | 避免 |
| --- | --- | --- |
| Dashboard 不开 | 从托盘重新打开，记录 selected port/service identity | 批量杀 Python/Chrome |
| 8765 被占 | 允许 8766–8799 安全回退 | 强占端口 |
| 登录过期 | 在受管 Chromium 重新登录 | 复制 Cookie/profile |
| 好友要求重新关联 | 完整扫描后在 Friends 显式 relink | 按昵称直接覆盖 binding |
| `uncertain` | 查看结构化失败/日志，停止重复发送 | 手工重跑覆盖结果 |
| Scheduler 操作失败 | 看 UAC 结果和 drift/read error | 永久管理员运行 Dashboard |
| MSI/Repair 失败 | 校验 hash、保留 verbose log、确认 ProgramRoot/DataRoot | 删除 DataRoot “重置” |
| Release 资产不存在 | 使用最后已发布稳定版本 | 下载 CI 中间包冒充 Release |

更多维护步骤见 11《运维维护与故障排查》。
