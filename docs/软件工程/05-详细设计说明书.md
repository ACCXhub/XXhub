# AutoDy 详细设计说明书

## 1. 设计约定

本说明从“谁拥有这项事实”出发描述当前实现。文件名是定位线索，真正的边界由模型、状态转换和调用契约定义。业务逻辑应通过现有 owner 协作，不在 Web API、前端或脚本中复制第二套规则。

## 2. 配置与 Target

### 2.1 Owner

`src/autody/config.py`

### 2.2 核心模型

`Target` 持有：`name`、`enabled`、`note`、`stable_id`、`candidate_id`、`binding_identity_key`、`binding_identity_source`、`binding_account_scope`、目标级文案包/后缀/延迟/选择方式/顺序。

`AppConfig` 持有全局目标列表、文案/浏览器/状态/锁/工件路径、重试/超时、文案后缀、默认文案包、三类计划时间、恢复截止时间、随机延迟、页面/好友/确认超时、目标顺序/文案选择、通知、preflight、日志保留和好友扫描参数。

关键校验：稳定 ID 与 candidate ID 分别唯一；恢复截止时间不能早于每日发送时间；最小延迟不能大于最大延迟；归档日志保留期不能短于活跃日志保留期。

写入使用临时文件、flush/fsync 和 `os.replace`，避免一半写入。相对路径以 `config.yaml` 所在目录解析。

### 2.3 可执行目标

`enabled_execution_targets()` 保持 legacy name-only 配置兼容；一旦配置中已经存在 candidate binding，则现代可执行目标必须 `enabled + stable_id + candidate_id`。这使未完成迁移/失联 Target 不进入计划和 sender。

## 3. 好友发现

### 3.1 Owner

`src/autody/friend_discovery.py`

### 3.2 输出

完整 discovery 输出 `discovered_friends.json`，候选是 `FriendCandidate`；过程状态写 `friend_scan_progress.json`；头像写 `avatar-cache/`。完整 cache 默认 24 小时 TTL，头像默认 7 天 TTL。

候选记录当前 candidate ID、显示名、头像状态、发现/最后出现时间、scan ID、presence、权威 identity key/source 与 conversation locator。`FriendDiscoveryResult` 还记录本次 scan 是否成功、account scope 和 targeted refresh 证据。

### 3.3 完整性原则

虚拟列表需要滚动并等待 lazy-load；只有完整、当前、成功的扫描才能成为自动绑定恢复的输入。扫描失败或取消不得用空结果覆盖上一次有效事实。

## 4. 稳定绑定与显式重关联

### 4.1 Owner

`src/autody/binding_recovery.py`

`resolve_stable_binding()` 是读取/运行时唯一权威解析；`reassociate_stable_binding()` 是显式重新关联的写入入口。

### 4.2 三层身份

- `stable_id`：AutoDy Target 主键。
- `binding_*`：账号范围内 durable friend proof。
- `candidate_id` / `conversation_id`：当前 discovery/会话 locator。

不能把 locator 或 display name 当 durable friend identity。当前 React conversation model 中可验证的参与者身份是 durable proof 来源，conversation id/shortId 只用于当前导航。

### 4.3 解析结果

解析可返回健康或 `binding_missing`、`stale_locator`、`identity_ambiguous`、`account_mismatch`、`account_unverified`、`scan_unavailable/incomplete/failed/stale`、`revalidation_required` 等状态。Runner、Friends 和 Overview 应消费同一解析结果，不各自推断健康。

### 4.4 写回条件

重新关联必须同时满足：目标存在；candidate 当前且未被其他 Target 占用；discovery 完整；account scope 一致；identity source 在权威 allowlist；identity 唯一匹配。满足后才更新 identity key/source、account scope 和当前 locator。

## 5. 账号资料与多账号

### 5.1 `account_profile.py`

负责当前已验证 Douyin 账号的本地元数据、头像、account scope 比较和 logout revalidation guard。原始平台账号 ID 不直接作为公开 payload；缓存使用 digest/本地 profile ID。

退出前先写 `account-binding-state.json = revalidation_required`，即使清理认证中途失败，旧 binding 也不会被当作已验证会话继续发送。

### 5.2 `account_profiles.py`

`MultiAccountStore` 负责 `data/account-profiles/registry.json`、每账号 `account-settings.json`、browser-profile 和 runtime snapshots。切换流程是：检查互斥 → snapshot 当前账号 → 清空兼容 working set → 恢复目标账号 → 更新 config/profile_dir → 保存 registry。

首次 legacy migration 在 `account-profile-migration-backups/` 建备份和 rollback manifest；任何失败恢复 config/browser 状态。

## 6. 状态、历史和重试

### 6.1 `state.py`

`state.json` 保存文案 rotation 和按日期的 daily 状态。daily 是兼容/当日投影基础，不应单独替代结构化 history/outcome。

### 6.2 `history.py`

`history/task-runs.jsonl` 追加 `TaskRunRecord`：run_id、日期、任务类型、触发源、时间、计数、终态、文案标识、失败 Target、确认结果和 `FailureDetail`。读取时跳过损坏行并在 integrity 中报告 invalid_count。

### 6.3 `retry_state.py` 与 Runner

`history/task-outcomes.json` 记录自动重试状态。`runner.py` 使用确定的 daily run_id，把自动执行划分为：无需运行、完成、等待安全重试、恢复成功、最终失败、不确定、取消。

安全 pre-send failure 才能 schedule/retry；确认失败或已经有发送尝试会走 uncertain。到 recovery_deadline 后未完成的 safe retry 收敛为 final_failed。

## 7. Chat 发送管线

Owner 为 `chat.py`；编排 owner 为 `runner.py`。

Runner 传入 Target 和由 binding resolver 得到的 `expected_conversation_id`。Chat 负责在受管页面中验证预期会话、编辑器与发送动作，返回结构化 `DeliveryResult`。Runner 根据 `DeliveryStatus`、send_attempts、confirmation_attempts 和 reason_code 生成 `FailureDetail` 与终态。

全局 browser lock 防止真实发送、好友扫描、登录等浏览器任务并发操作同一 profile。调用者不能通过另起 Playwright 实例绕开此锁而仍宣称是产品发送路径。

## 8. Preflight

Owner 为 `preflight.py`。

`ReadOnlyPage`/`ReadOnlyLocator` 只提供查找、等待、受限 evaluate 和专门的 `open_conversation`。它没有通用 click/fill/type/press/send；evaluate 拒绝 dispatchEvent、click、focus、直接修改 value 等表达式。

流程：验证登录/聊天列表 → 唯一定位 Target → 仅打开会话行 → 检查 header → 检查 composer 是否存在/可见/可用 → 检查发送控件容器存在 → 返回 `Readiness`。持久结果写 preflight store，并记录所有消息写动作计数为 0。

## 9. Scheduler

Python owner 为 `scheduler.py`，Windows 写入由 `scripts/install-task.ps1`、`remove-task.ps1` 等既有脚本完成。

Dashboard 只提交计划配置或受约束操作；提升子进程只分派 install/remove 类已知入口。任务快照读取返回三态：成功有任务、成功空、读取失败；失败不能折叠为空。

任务验证关注名称、触发时间、脚本、ProgramRoot、DataRoot、WorkingDirectory、Principal、RunLevel 和重复窗口。Repair 在 transient snapshot read error 上有限重试，但不会把真实 drift 自动“修成通过”。

## 10. Web API

Owner 为 `web_api.py`。它承担 HTTP 适配、Pydantic 请求验证、读取/写入 owner 调用、ActionManager 异步动作状态和前端静态资源，不应复制 binding/send/Scheduler 的业务判定。

- 只读资源直接返回当前模型投影。
- 长时间浏览器动作通过 `/api/actions/*` 返回 202/job，再读 job 状态。
- 业务冲突/安全阻断主要使用 409；请求格式/值错误使用 422；不存在使用 404。
- 所有 `/api/*` 未知路由明确 404，不落入 SPA fallback。

接口清单见 06。

## 11. 日志与备份

`log_center.py` 负责结构化日志查询、摘要、保留、归档和受控清理；诊断导出只含最近脱敏摘要。

`transfer.py` 负责备份 v2、类别选择、checksum/manifest、preview 和 merge/replace；Web API 继续兼容 legacy v1 backup，但导入前验证格式并在写入失败时恢复原 config/messages。

备份与诊断都不是整个 DataRoot 的镜像工具。浏览器 profile、Cookie、头像缓存和好友 discovery 等敏感/可再生成数据按设计排除。

## 12. 托盘与 watchdog

生产 owner 位于 `scripts/` 的托盘/控制脚本；Python 测试通过 `test_tray_controller.py`、`test_watchdog_controller.py`、`test_service_recovery_safety.py` 固化关键契约。

托盘保存受管进程快照（PID、路径、owner、creation time）并结合 `/api/service-identity` 验证。watchdog 恢复状态包含 health 连续失败计时、自动尝试时间窗、熔断和 manual-stop suppression。

强制停止只能发生在 graceful stop 失败且具体 PID 的 identity 再验证仍通过之后；禁止按 `python.exe` 名称批量结束。

## 13. MSI 与发布

### 13.1 MSI

WiX owner 为 `packaging/wix/`，构建脚本位于 `scripts/`。MSI 表和 CustomAction 必须保持 ProgramRoot/DataRoot、原用户身份、Scheduler repair/rollback/uninstall 的精确契约。

Lifecycle verifier 在干净 Windows 环境真实执行 UI/table 静态检查、fresh install、Repair、默认卸载、自定义安装/卸载、上一版本迁移/当前安装、最终卸载和数据快照检查。

### 13.2 Release

`release_build` marker 标记两项大型可重复性测试；普通 CI 排除它们。Release workflow 从 tag clean source 运行这些测试并构建 canonical artifacts，随后 privacy/package → lifecycle → manifest → publish → public reverify。

v1.5.0 workflow 的构建和 privacy/package 曾通过，但 lifecycle 失败且没有发布资产。当前 v1.5.1 必须从自身 tag clean source 重新完成 build、privacy/package、lifecycle、publish 与 public reverify。

## 14. 前端

`frontend/src` 只消费 API payload 和发起用户操作。Dashboard/Friends 等页面不能根据名字自行推断 binding，也不能用当前 UI 数量作为独立业务事实；Overview 今日总数、好友状态和资源投影来自后端同一 executable target set。

产品 UI 的异步动作需要明确 loading/success/failure，不通过连续点击制造重复请求。Friends 的重新关联只调用后端 canonical relink API。
