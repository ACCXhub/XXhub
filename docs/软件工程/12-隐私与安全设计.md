# AutoDy 隐私与安全设计

## 1. 安全目标与信任边界

AutoDy 的信任边界是当前 Windows 设备和用户控制下的受管 Douyin 会话。系统只在本机 loopback 提供 Dashboard/API，不设计远程控制或云端账号数据服务。

主要安全目标：

- 不把错误好友/会话当作正确目标；
- 不因失败重试造成重复发送；
- 不停止无关进程或接管未知服务；
- 不因安装/升级/卸载删除用户 DataRoot；
- 不把真实账号、消息、Cookie、browser profile、日志/备份带入 Git、Release 或普通诊断；
- 需要提升时只提升最小操作，Dashboard 和 Scheduler 正常保持原用户/Limited 边界。

## 2. 数据分类

| 数据 | 级别 | 允许用途 | 不允许流向 |
| --- | --- | --- | --- |
| Program payload/version/manifest | Public/Program | 运行、发布、验证 | 无特殊私密限制 |
| selected port、匿名 run ID、reason/stage | Local | 状态/脱敏诊断 | 不应关联真实账号内容 |
| Target、display name、文案、历史、好友缓存、账号显示资料 | Private | 本机产品功能 | Git、公开文档/诊断、Release 用户数据 |
| Cookie、browser profile、local storage、认证令牌 | Auth-sensitive | 受管浏览器登录 | API 导出、备份、日志、工单、Release |

完整路径和字段见 07。

## 3. 好友身份安全

### 3.1 身份分层

- Target `stable_id`：AutoDy 内部业务主键；
- durable friend proof：`binding_account_scope + binding_identity_source + binding_identity_key`；
- candidate/conversation locator：当前 discovery 导航证据。

昵称、头像、DOM 顺序、candidate_id 或 conversation locator 都不能单独成为永久好友 identity。完整 discovery、account scope、权威 identity source、唯一性和未占用条件同时满足后才允许自动/显式关联。

### 3.2 Fail closed

以下状态不自动写 binding：扫描部分完成/失败/取消/过期、登录未验证、账号不一致、identity 缺失/歧义、candidate 已被其他 Target 占用、只有名称/头像证据。

显式“重新关联”仍必须通过同一 canonical resolver/reassociate 契约，不能因为用户点了按钮就绕过身份证明。

## 4. 发送安全

发送前按顺序确认：

1. 当前 Target 属 executable set；
2. account scope/binding proof 有效；
3. 当前 conversation locator 唯一且符合预期；
4. 全局 browser lock 已取得；
5. 当日重复保护允许；
6. 编辑器/页面状态允许；
7. 执行一次发送；
8. 进行确认并记录结构化结果。

只有 `send_attempts=0` 且失败发生在发送动作前才能安全 retry。发送已尝试但无法确认时进入 `uncertain`，历史保留且自动 retry 不可用。恢复 binding/账号不能把旧 uncertain 自动变成 safe retry。

## 5. Preflight 安全

Preflight 与 sender 解耦。`ReadOnlyPage/Locator` 没有 fill/type/press/send API，evaluate 明确拒绝会修改页面的常见表达式。唯一允许的页面点击是打开候选会话行，以读取 header/composer 状态；它不焦点编辑器、不改变 value、不发送。

持久 preflight 证据记录写动作计数，正常必须为 0。Test Center 的 dry-run/fixture 也不能成为绕过真实 send safety 的第二发送管线。

## 6. 浏览器与账号数据

受管 browser profile 可能含 Cookie/local storage/IndexedDB 等认证数据，属于 Auth-sensitive：

- 不通过普通 API/diagnostic/backup 导出；
- 不进入 Git/Release；
- 不要求用户复制日常浏览器 profile；
- logout 只清理 AutoDy-managed Douyin 认证 origin/cookies，并先写 binding revalidation guard；
- 多账号 browser profile 物理隔离，切换由 `MultiAccountStore` 负责 snapshot/restore。

账号公开 payload 只返回必要的本地 profile/digest/display metadata，不把原始认证当调试信息输出。

## 7. 并发与锁

真实浏览器任务使用全局 lock；账号切换/退出与受管 browser action 互斥。锁获取失败应报告 busy/409，不通过并发打开第二 profile 或强制删除 lock 文件解决。

同日重复发送由状态/history/outcome 共同保护；用户刷新页面、重复点击或托盘重启不能绕过该保护。

## 8. 服务身份与进程安全

端口和 PID 都是 locator，不是 ownership proof。托盘结合：

- `/api/service-identity`；
- 当前 Windows 用户；
- application/version；
- ProgramRoot/package path；
- Python executable；
- managed process PID/path/owner/creation time。

只有匹配的服务可以复用/停止。8765 被其他应用占用时换用 8766–8799，未知进程保持存活。禁止按 `python.exe` 名称或端口批量终止进程。

## 9. Watchdog 安全

watchdog 不是通用“杀死并重开”脚本：

- 进程退出与“进程存在但 health 失败”分开；
- health 连续失败约 15–20 秒才判 hung；
- 优先正常退出；
- 强制停止前再次验证 exact PID ownership；
- 10 分钟最多 3 次自动恢复，之后熔断；
- explicit full exit 产生同日 suppression；
- 自动恢复只恢复服务，不发送、不 discovery、不 Scheduler repair、不修改无关 DataRoot。

这些限制防止 transient network/health 波动演变为无限重启或误杀。

## 10. Scheduler 与 UAC

Scheduler 自动任务使用原交互用户 Principal、`RunLevel Limited`。Dashboard 常态非提升；安装/修复/移除/应用 Task 通过一次性受约束 `runas` PowerShell 子进程。

提升前捕获 SID、ProgramRoot、DataRoot；提升后不能使用管理员环境 `%LOCALAPPDATA%` 重新推断用户。提升入口只分派到已知 install/remove task scripts，不能接受任意命令。

短生命周期结果文件只包含必要操作结果并及时删除，不包含账号/目标/消息/Cookie。

## 11. MSI 与数据保留

MSI per-machine ProgramRoot 和原用户 DataRoot 分离。普通卸载删除程序/快捷方式/AutoDy Tasks，但默认保留 DataRoot。永久删除 DataRoot 是用户单独确认后的不可逆操作，不能隐藏在 Repair/卸载/“清理”按钮中。

Installer 必须拒绝陈旧/未知路径，不向仅因 Registry 还存在的错误目录补写 payload。1.4.0–1.4.2 per-user 到 1.4.3+ per-machine 的 scope migration 保留 Permanent DataRoot。

## 12. 备份与日志最小披露

新备份使用类别 allowlist + manifest/checksum；普通 backup 不包含 browser profile。legacy v1 import 只保留向后兼容，不扩大新导出范围。

日志用于阶段/错误/状态诊断，不用于复制会话。diagnostic ZIP 只包含 masked recent summary，显式排除消息正文、Cookie、browser profile、avatar-cache、`discovered_friends.json`。日志共享前还应人工检查路径/堆栈是否泄露本机资料。

## 13. Release 供应链边界

构建采用 allowlist 和 fixed runtime inputs，不递归复制工作仓库。正式 Release 验证：

- immutable historical tag/上一稳定 MSI baseline；
- clean-source heavy reproducibility tests；
- portable/MSI 的 manifest、CAB/native runtime/CustomAction；
- privacy/path/content scan；
- MSI lifecycle；
- publish 后 re-download 和 hash/manifest/MSI/privacy 再验证。

任何门禁失败都不执行后续 publish。CI artifact/本地 MSI 不能冒充正式资产。

v1.5.0 正式 workflow 曾通过 build/privacy/package，但 lifecycle 失败且没有发布资产。v1.5.1 不继承这项部分结果，仍需从自身 tag 完成全部供应链验收。

## 14. Git 与文档隐私

仓库忽略 DataRoot、browser profile、logs、cache、`.venv`、`node_modules` 和 build outputs。软件工程文档只使用 `%LocalAppData%\AutoDy`、`D:\AutoDy`、`<selected-port>`、`<日志路径>` 等通用示例，不记录真实账号/目标/消息/个人路径。

安全问题文档应记录类别/影响/修复，不把敏感原文再次复制到 issue/report。

## 15. 威胁与控制矩阵

| 威胁 | 主要控制 |
| --- | --- |
| 重名/locator 变化导致误发 | durable identity + account scope + unique current resolver |
| 发送后确认失败导致重复 | uncertain terminal + no auto retry |
| 浏览器任务互相干扰 | global browser lock + account-change guard |
| 未知服务被停止 | service identity + process ownership + exact PID revalidation |
| health 波动造成重启风暴 | 15–20s hysteresis + 3/10min circuit breaker |
| 管理员环境写错 DataRoot | pre-elevation original SID/LocalAppData + explicit roots |
| 卸载删除用户数据 | ProgramRoot/DataRoot separation + Permanent DataRoot |
| 私密文件进入安装包 | build allowlist + privacy verifier |
| CI 中间产物被误发 | Release workflow guard + public reverify |
| 恶意/损坏 backup 覆盖本机 | preview/schema/checksum + rollback |

## 16. 安全变更准入

以下改动一律视为安全变更：friend identity、sender/confirmation/retry、browser lock、账号切换、进程停止、watchdog、Scheduler Principal/UAC、ProgramRoot/DataRoot、backup/export、release allowlist/verifier。

安全变更必须明确：新增数据流、失败行为、未知外部状态处理、恢复边界和聚焦测试；不能只验证正常路径。
