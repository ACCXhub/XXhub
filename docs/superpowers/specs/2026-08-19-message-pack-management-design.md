# AutoDy 可逆文案包管理设计

## 1. 范围与目标

本设计只覆盖文案包管理工作流，不包含启动性能优化，也不改动 Dashboard、Douyin 发送安全语义、Scheduler 任务语义或 BrowserWeave。

目标是在保留现有全局 `messages.txt` 文案库和发送兼容链路的前提下，引入一套用户可管理的文案包目录，支持稳定身份、空包创建、TXT 导入、改名、消息增删改、顶层排序、可逆融合、嵌套谱系、拆分和安全删除。

## 2. 已确认的产品决策

1. 全局 `messages.txt` 继续作为独立兼容来源，不迁移成普通文案包。
2. 新文案包以稳定 ID 被目标配置引用；改名不改变 ID。
3. 现有内置包只在新目录首次初始化时种入一次，保留原有 pack ID；种入后成为完全普通的用户包。
4. 后续升级不得覆盖、重置或复活已种入、已编辑或已删除的内置包。
5. 一次性种入由明确的 migration 状态控制，绝不以“目录是否为空”作为判断条件。
6. 融合 `A → B` 时，所有当前指向 A 的目标引用原子迁移到 B；拆出 A 时不自动回滚引用。
7. 后续未单独确认的架构选择采用本文推荐方案。

## 3. 方案比较

### 3.1 推荐：单一版本化目录文档

在 DataRoot 下保存一个小型版本化 JSON 文档，完整包含包、消息、顶层顺序、融合树和 migration 状态。每次目录变更先在内存验证完整新状态，再通过临时文件与 `os.replace` 原子提交。只有融合需要同步迁移目录外的目标引用，因此额外使用第 12 节定义的小型可恢复事务。

优点：符合现有 JSON/文本持久化风格；无需新依赖；单次读取即可得到目录；拆分、排序和目录侧融合都只需一次目录文件替换；数据量很小，不会对启动造成可感知扫描成本。

### 3.2 未采用：每包一个文件加目录索引

该方案在人工查看时更直观，但融合、拆分、排序和递归删除会同时修改索引、多个包文件及消息文件，需要通用多文件事务和恢复协议。复杂度与当前数据规模不匹配。

### 3.3 未采用：SQLite

SQLite 能提供天然事务，但会为数百条短文本引入新的持久化子系统、迁移工具和备份兼容面。AutoDy 当前没有数据库依赖，本功能不足以证明该成本合理。

## 4. 存储位置与目录文档

权威用户目录位于：

```text
<DataRoot>/data/message-packs/catalog.json
```

跨进程写锁位于：

```text
<DataRoot>/data/locks/message-packs.lock
```

只在融合需要同步迁移外部包引用时使用的恢复日志位于固定路径：

```text
<DataRoot>/data/message-packs/pending-transaction.json
```

目录文档使用以下结构和字段名：

```json
{
  "schema_version": 1,
  "revision": 12,
  "migrations": {
    "builtin_seed_v1": {
      "completed": true,
      "completed_at": "2026-08-19T20:00:00"
    }
  },
  "top_level_pack_ids": ["daily", "pack-uuid"],
  "packages": {
    "daily": {
      "id": "daily",
      "name": "日常",
      "description": "",
      "created_at": "2026-08-19T20:00:00",
      "items": [
        {"kind": "message", "message_id": "message-uuid"},
        {
          "kind": "fused_source",
          "pack_id": "morning",
          "fused_at": "2026-08-19T20:10:00",
          "restore_index": 1
        }
      ]
    }
  },
  "messages": {
    "message-uuid": {
      "id": "message-uuid",
      "text": "早安",
      "created_at": "2026-08-19T20:00:00",
      "updated_at": "2026-08-19T20:00:00"
    }
  }
}
```

`top_level_pack_ids` 是唯一顶层排序权威。包的 `items` 是内容顺序权威：消息节点引用一条消息；融合节点引用一棵完整来源包子树。顶层包是 `top_level_pack_ids` 中的包；融合来源包仍保留完整包记录和稳定 ID，但不在顶层数组中。

目录文件即使没有任何包也必须继续存在，并保留 `builtin_seed_v1.completed = true`。用户删除全部包不会触发再次种入。

## 5. 稳定身份与数据约束

### 5.1 包 ID

- 首次种入的内置包沿用当前 `index.json` 中的稳定 slug ID，保证旧 `Target.message_pack` 引用继续有效。
- 新建和导入包使用随机 UUID 生成不可变 ID。
- 包名不是身份键，允许两个不同包使用相同显示名。
- 包名保存前去除首尾空白，按 Python 字符串长度计算最多 80 个 Unicode 码点；用户改名超过限制时拒绝保存。

### 5.2 消息 ID

- 每条消息有独立随机 UUID；正文不作为身份。
- 相同正文可以在同一包或不同包中多次出现。
- 编辑只更新该消息记录的 `text` 与 `updated_at`，ID 不变。
- 删除同时移除消息节点与消息记录，拆分时不得恢复已删除正文。

### 5.3 完整性约束

每次加载和提交前验证：

- schema 版本受支持；
- migration 状态存在且类型有效；
- 包 ID、消息 ID 唯一，记录内 ID 与映射键一致；
- 顶层数组无重复且只引用存在的包；
- 每个非顶层包恰好被一个融合节点引用；
- 每条消息恰好被一个消息节点引用；
- 不存在孤儿、重复成员或融合环；
- 融合树深度和总节点数在实际目录规模内可完整遍历。

无效或损坏目录必须明确报错，不能静默清空、重建或重新种入。

## 6. 首次迁移与旧版本兼容

首次访问新目录时，在跨进程写锁内执行以下确定性流程：

1. 若 `catalog.json` 已存在，加载并验证；绝不根据包数量重新种入。
2. 若文件不存在，从当前 ProgramRoot 的发布内置 `message-packs/index.json` 和对应 TXT 读取五个旧包。
3. 保留旧包 ID、名称和说明；为每一行创建独立消息记录并保持顺序。
4. 旧发布包原来会按正文去重；种入时保持当前有效预览语义，避免升级后同一旧包突然增加历史重复项。
5. 同一次原子提交写入包目录和 `builtin_seed_v1.completed = true`。
6. 若内置索引或文件无效，初始化失败并明确报告，不写半成品目录或完成标记。

源代码运行和安装版均从各自 ProgramRoot 读取发布内置包。DataRoot 根目录下由旧启动器复制的 `message-packs` 目录不是新用户目录权威，也不能覆盖 `catalog.json`。

现有全局 `messages.txt`、`/api/messages`、消息轮换和发送选择逻辑保持不变。只有目标明确选择文案包时，包内容读取从旧只读内置服务切换到新目录服务；旧 pack ID 仍能解析。

## 7. 导入与空包创建

### 7.1 新建空包

“新建文案包”立即创建一个无消息、无融合来源的普通包，默认名为 `新建文案包`，追加到顶层顺序末尾并在 UI 中打开编辑状态。重名不影响创建。

### 7.2 TXT 导入成新包

导入是独立于全局文案导入的新领域操作：

1. 只接受 TXT 文本；使用 UTF-8 解码，解码失败整次拒绝。
2. 按换行拆分；仅丢弃 `line.strip()` 为空的行。
3. 非空行正文按文件内容保存，不做语义改写、模糊去重或精确去重；重复行得到不同消息 ID。
4. 保持原始行顺序。
5. 单条消息沿用现有 500 字符安全上限。任一非空行超限时整次导入失败，报告行号；绝不截断正文或创建部分包。
6. 第一条有效消息去除用于显示名无意义的首尾空白后成为初始包名。
7. 初始包名超过 80 字符时使用前 79 字符加 `…`；完整消息正文仍原样保存。
8. 没有有效消息时拒绝导入，不创建空的失败产物。

## 8. 包和消息编辑

- 改名只更新包名，不改变包 ID、消息 ID、顶层位置、谱系或目标引用。
- 新增消息总是追加到当前顶层目标包的 `items` 末尾；即使该包包含融合来源，也归属于当前目标包，不猜测旧来源。
- 编辑从聚合视图中定位稳定 message ID，并更新当前正文；来源分组不变。
- 删除消息移除当前记录；以后拆分不会复活。
- 第一版不增加消息拖动排序。顶层包排序是明确需求，消息顺序沿创建、导入和融合操作自然保存。

## 9. 顶层排序

拖动结果通过一次 API 请求提交完整 `top_level_pack_ids`。服务端要求该数组与当前顶层 ID 集合完全相等且无重复，然后规范化保存。

刷新、进程重启和正常数据重载始终读取该数组，不再由名称、创建时间或文件顺序推导。UI 同时提供“上移/下移”操作，确保不使用拖动也能改变顺序。

前端不新增拖放依赖。AutoDy 是 Windows 桌面优先应用，简单列表使用原生 HTML drag events，并以按钮提供键盘替代，避免为一个排序列表引入 UI 框架。

## 10. 可逆融合与拆分

### 10.1 融合

融合只允许两个不同的顶层包。执行 `A → B` 时：

1. 验证 A、B 存在、均为顶层且操作不会形成环。
2. 从 `top_level_pack_ids` 移除 A。
3. 在 B 的 `items` 末尾追加引用 A 的 `fused_source` 节点。
4. 节点记录 `fused_at` 和 A 融合前的顶层索引 `restore_index`。
5. A 的包记录、内部消息节点和已有融合子树完全不变。
6. 所有当前指向 A 的持久化目标引用迁移到 B。

聚合内容按包的 `items` 顺序递归展开。因此 B 的原内容在前，A 的完整内容随后；融合后向 B 新增的消息节点会真正追加到聚合内容末尾。

### 10.2 嵌套融合

若 A 已融合进 B，随后 B 融合进 C，C 只新增一个引用 B 的融合节点；A 仍留在 B 的内部序列中，不扁平化到 C。数据关系为：

```text
C
└─ B
   └─ A
```

完整性验证对整个引用图做深度优先遍历，拒绝自引用、祖先引用、重复父节点和任何环。即使 API 当前只允许顶层融合，底层仍执行完整环检测，避免损坏数据绕过 UI。

### 10.3 拆分

“拆出已融合包”只列出当前包的直接融合来源，不在普通列表暴露原始 ID 或完整树。拆出 A 时：

1. 从父包 `items` 移除引用 A 的融合节点。
2. 将 A 插回顶层数组的 `min(restore_index, current_length)` 位置。
3. A 的当前消息正文、当前剩余消息以及自身已有融合子树保持不变。
4. 父包不再聚合 A 子树内容。
5. 不自动把任何目标引用迁回 A。

若要从 `C → B → A` 中拆出 A，先从 C 拆出 B，再从 B 拆出 A。普通 UI 不提供任意深度树编辑器。

## 11. 删除语义

- 删除普通顶层包会删除该包及其全部消息。
- 删除含融合来源的顶层包会递归删除整棵融合子树、所有消息和谱系节点。
- UI 确认文案必须明确显示将删除的消息总数和嵌入来源包数量。
- 若该顶层包仍被任何目标配置引用，删除返回冲突并要求先重新选择来源或融合到另一个包；绝不静默退回全局 `messages.txt`。
- 目录提交前验证没有孤儿包、孤儿消息或悬空融合节点。

## 12. 并发、原子性与恢复

所有写操作使用独立 `message-packs.lock` 跨进程排他锁。读操作只读取一个经原子替换生成的完整 JSON 文件，因此只能看到提交前或提交后的完整版本。

单目录操作在内存构造完整新文档、验证全部约束、写同目录唯一临时文件、刷新后通过 `os.replace` 提交。失败时删除临时文件，原目录保持不变。

融合还需要修改现有目标配置引用。该操作使用固定 pending journal：

1. 在锁内计算并验证新目录和新配置的完整字节内容。
2. 原子写入包含事务 ID、目标路径、旧内容、新内容及各自哈希的 pending journal。该文件属于 DataRoot 内的临时核心运行数据，不记录到应用日志，事务结束后立即删除。
3. 对目录与配置逐个执行幂等原子替换。
4. 全部成功后删除 journal，再向 API 返回成功。
5. 普通写入异常时，使用 journal 中的旧内容幂等回滚所有目标文件，验证原状态恢复后删除 journal 并返回失败。
6. 若进程在中途退出，下一次目录访问只检查该固定文件；存在时在同一锁内校验并幂等完成剩余替换。

该机制保证不会长期保留半融合状态，也不在启动时扫描事务目录。普通失败在返回前保持或恢复完整状态；崩溃恢复采用确定性的 roll-forward。

## 13. API 设计

沿用 `/api/message-packs` 前缀，扩展现有 API，不创建平行子系统。推荐端点：

```text
GET    /api/message-packs
POST   /api/message-packs
POST   /api/message-packs/import
GET    /api/message-packs/{pack_id}
PATCH  /api/message-packs/{pack_id}
DELETE /api/message-packs/{pack_id}
PUT    /api/message-packs/order
POST   /api/message-packs/{pack_id}/messages
PATCH  /api/message-packs/{pack_id}/messages/{message_id}
DELETE /api/message-packs/{pack_id}/messages/{message_id}
POST   /api/message-packs/{source_id}/fuse
POST   /api/message-packs/{destination_id}/split
```

融合请求携带 `destination_id`，拆分请求携带直接来源 `source_id`。所有写响应返回新的目录 revision；客户端在提交排序和编辑时携带预期 revision，过期写返回冲突并要求刷新，避免两个页面互相覆盖。

现有 `POST /api/message-packs/{pack_id}/import` 继续表示“将所选包内容导入全局 `messages.txt`”，以兼容旧能力。新 TXT 创建包使用独立的集合级 import 端点。现有预览响应保留 `messages: string[]`，并扩展带稳定 ID、来源包名和可编辑性的 `entries`，旧客户端不因新增字段失效。

HTTP 错误区分：不存在为 404；非法输入和环为 422；revision、被引用删除和写锁占用为 409；目录损坏或不受支持 schema 为 503。错误响应使用可直接展示的中文摘要，不返回本机私有正文或内部路径。

## 14. UI 设计

文案包页保留现有字体、间距、按钮和面板语言，改为紧凑列表：

```text
☰ 日常       20 条       …
☰ 早安       16 条       …
☰ 简短       25 条       …

+ 新建文案包    + 导入文案
```

- 行级菜单包含：重命名、编辑、融合到、拆出已融合包、导入到全局文案库、删除。
- 只有存在直接融合来源时显示“拆出已融合包”。
- 新建、改名和消息编辑使用行内或同页详情面板，不为普通操作叠加多个 modal。
- 融合使用目标包选择和一次明确确认；不能选择自身或非顶层包。
- 拆分面板显示可拆出的来源包名和当前消息数，不显示原始 ID。
- 编辑聚合内容时，融合来源消息可显示低强调度来源标签，帮助解释拆分结果；新增入口始终属于当前顶层包。
- 删除含融合来源的包时使用现有 `window.confirm` 风格，明确递归范围。
- 拖动句柄支持鼠标拖动；行菜单提供上移、下移作为键盘和非拖动替代。

## 15. 备份与导入兼容

现有备份格式已经预留 `message-packs.json`，但当前只写空对象。实现后该类别导出完整、已验证的目录文档，仍与独立的 `messages.txt` 类别分开。

- 旧备份中的空对象视为“没有可恢复的新式文案包”，不得清空当前目录。
- replace 导入完整替换文案包目录前先验证 schema、引用树和消息成员。
- merge 导入按稳定 ID 合并；无冲突 ID 直接加入，内容完全相同的 ID 跳过，结构冲突的 ID 分配新 UUID，并在导入子树内一致重写包和消息引用。
- 导入过程不重置 `builtin_seed_v1.completed`，也不触发内置包重新种入。
- 备份导入产生的目录仍通过同一锁、完整性验证和原子替换提交。

## 16. 启动性能约束

目录加载不得扫描每包文件或在每次启动重建索引。正常路径只读取一个小型 JSON 文件；首次 seed 只执行一次。migration 标记随目录保存，空目录不会触发重复工作。

pending 事务恢复只检查一个固定文件是否存在，不枚举历史事务。该设计不得显著增加已测得的服务监听或首个 Dashboard 状态响应时间。

## 17. 测试策略

后端领域测试至少覆盖：

- 首次种入保留旧包 ID，旧目标引用继续解析；
- migration 完成后删除全部包，重载和升级均不重新种入；
- 空包创建、改名保持稳定 ID；
- TXT 首条有效行生成名称、长名称截断而正文不变、空行删除、重复正文保留不同 ID、超长行整次失败；
- 顶层排序刷新和重新实例化后保持；
- A 融合进 B 后 A 不在顶层、内容按序聚合、来源可恢复、目标引用迁到 B；
- 融合后编辑和删除来源消息，拆分得到当前内容而非历史快照；
- 融合后新增消息属于目标原生包并出现在聚合末尾；
- `A → B → C` 后拆出 B，B 仍含 A；
- 自引用、祖先环、重复父节点和损坏目录被拒绝；
- 拆分不回滚目标引用；
- 删除含融合来源的目标包递归清理，仍被引用时拒绝；
- pending journal 中断后幂等恢复完整状态；
- 旧空 `message-packs.json` 备份不清空新目录。

API 测试覆盖所有领域端点、revision 冲突、错误码和旧 import-to-global 兼容端点。发送侧测试确认全局 `messages.txt` 路径和选择算法不变，并确认旧稳定 pack ID 由新服务返回相同有效消息。
